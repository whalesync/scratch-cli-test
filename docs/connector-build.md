# Connector-build playbook — cross-connector tricks & problems

Helper file for the **`/connector-build`** skill. This is the **accumulated, cross-connector** catalog of edge cases, tricks, and gotchas. The per-connector coverage lives in each connector's `STATE.md`; **this file is the shared memory** so every new connector starts forewarned.

**How to use:** read this at **Step 0** before building/testing a connector — it's organized by **type of trickiness**, not by connector, so you can scan the _kinds_ of problems to watch for and recognize them on the connector in front of you. The **deep, connector-specific specifics live in each connector's `STATE.md`**; this file keeps only the _type_ + a one-line example per connector + a pointer. When you discover a new quirk (Stage E): write the full specifics in the connector's `STATE.md`, then **add a one-line example under the matching trick type here** (or open a new type if it's genuinely new). Keep the entries here terse; the compounding _taxonomy_ is the point.

## Edge-case categories to ALWAYS probe (Pass 2)

A checklist of where connectors tend to misbehave. Run each entity/field through these, not just the happy path:

- **Field types:** boolean, date/datetime (timezone shifts?), single-select & multi-select (id vs label on write?), relation/FK, attachment/asset, formula/computed (read-only?), rich-text/HTML, JSON/nested objects, currency/number precision.
- **Boundary values:** empty string vs null vs missing key, very long strings, special characters / emoji / unicode, large arrays, 0 / negative numbers.
- **State & lifecycle:** status/stage transitions, draft vs published/live, archival/soft-delete vs hard-delete, restore.
- **Bulk vs single:** does the list/bulk endpoint return _everything_, or is some data (content, sub-resources) only available record-by-record?
- **Pull mechanics:** incremental vs full pull, records created mid-pull (pagination ordering), dedupe, deletions detected.
- **Write mechanics:** partial updates (changedFields only), read-only fields silently dropped, required fields on create, server-assigned ids/defaults flowing back.
- **Relations:** FK as a field on the record vs a separate association/relationship endpoint.
- **Auth & limits:** OAuth vs API key (CLI can only do key/param auth), rate limits / 429 backoff, scopes/permissions per entity.

## Testing patterns (general — confirm with the user before adding new ones)

Reusable _ways to test_, not facts about one connector. The skill adds simple edge cases automatically but **asks before adding a new pattern here**, because these shape every future run.

- **CLI-first, browser-where-it-counts.** The CLI is local and much faster than clicking a web UI — do reads, edits, creates, deletes, FK wiring, and verification with `scratchmd` whenever possible. Use the browser for the two things only it can do: **seeding data through the service UI** (when there's nothing to pull yet) and **confirming a change landed in the UI** the way a user sees it.
- **Two-workbook round-trip (push-then-pull-elsewhere).** Connect the **same service to two workbooks**. Make a change in workbook A and push it; then **pull in workbook B** and confirm the change is there and reads back cleanly. This proves the write genuinely reached the service (not just Scratch's `main`) and that it survives a fresh read — stronger than a same-workspace pull, which can replay pending local patches.

## Trick types (the catalog — scan these against the next connector)

Each entry is a _kind_ of trickiness with a one-line tell and brief per-connector examples. **Full specifics live in each connector's `STATE.md`** (linked); add a one-line example here when you hit a new instance, deep notes there.

### Fetch / read

- **Heavy fields (N+1 fetch).** A field's real payload is **not** in the bulk/list endpoint and must be fetched **per record** — turning a 1-page pull (1 call) into **N+1 calls**. Tell: list returns metadata/stubs, real content needs a per-id call. Examples: **Notion** page content/blocks (`notion/STATE.md`), **YouTube** transcripts (`youtube/STATE.md`). Plan the pull as light-list + heavy-hydrate; mind rate limits.
- **Bulk vs single field-set mismatch.** The single-record GET returns a **different set of fields** than the list/search endpoint. Tell: a field present in list is missing from get-by-id (or vice-versa). **Verify writes with the same read path the connector uses**, not get-by-id. Example: **GoHighLevel** `GET /contacts/{id}` omits `companyName`/`city`/… that search returns (`gohighlevel/STATE.md`).
- **Reference/config entities & missing get-by-id.** Not every entity round-trips — some are reference/config (pull-only), and a reference object may have **no get-by-id** (must refetch the list and filter). Example: **GoHighLevel** writable subset; Pipelines (no get-by-id) (`gohighlevel/STATE.md`).
- **Incremental "support" that's silently ignored (HTTP 200 ≠ honored).** Before wiring incremental, **prove the modified-since filter actually NARROWS** — pass a _future_ date and confirm the count drops to 0. A surprising number of APIs accept an unknown `filter`/`min_last_modified`/`updated_since` param, return **HTTP 200**, and quietly return the **full set**. Tell: filtered count == unfiltered count. Per-entity, not per-API: **Affinity** v2 honors `filter=updatedAt>=…` on **Notes only**; persons/companies/list-entries (and v1 `min_last_modified`) all ignore it, and list-entries carry no row-modified timestamp at all — so the connector stays full-pull and DEV-10159 was correctly canceled (`affinity/STATE.md`). Don't trust the docs or the status code; run the future-date count test.
- **`updatedAt`-null on never-edited records breaks an updatedAt watermark.** Even where a modified-since filter _is_ honored, an `updatedAt>=watermark` incremental **drops records whose `updatedAt` is null** (never edited since creation) — a brand-new record created after the watermark with null `updatedAt` is silently missed = data loss. Tell: `updatedAt>=<old date>` returns far fewer than the full set, and the missing ones have `updatedAt: null` with a recent `createdAt`. A correct incremental needs `createdAt>=W OR updatedAt>=W` (which a single `x-scratch-last-modified-field` hook can't express). Example: **Affinity** Notes — 8/10 had null `updatedAt` (`affinity/STATE.md`).

### Field shape

- **Read shape ≠ write shape.** A field **reads** as one shape and **writes** as another; store the read shape verbatim, translate only on write. Examples: **ClickUp** `status` object→name, `priority` object→int, dates ms-string→ms-int (`clickup/STATE.md`).
- **State / bucket fields.** A field — usually a _status/state_ — is **more than a value: it moves the record into a different bucket**, especially at publish (draft vs live), so changing it is a **dedicated operation**, not a normal field write. Examples: **Webflow** draft↔published live state (`webflow/STATE.md`); watch for the same in any CMS/CRM with publish/approval stages.
- **Value containers: array-by-id vs flat keys.** Custom-field values may live in an **array addressed by field id** (write via a per-field endpoint) instead of flat top-level keys. Examples: **ClickUp** `custom_fields[]` → `POST /task/{id}/field/{field_id}`, **Copper** `custom_fields[]`; contrast Airtable's flat `fields{}` (`clickup/`, `copper/`).
- **A view CANNOT make an array element an editable column → reshape the array to a keyed object.** Scratch column paths are **plain object dot-paths** (`a.b.c`): on **read** an array is a leaf (`getByPath` bails the moment a segment isn't a plain object — _"arrays are leaves; we never index into them"_), on **write** `setByPath` substitutes `{}` for an array segment (so edits into an array silently don't round-trip), and schema **auto-columns recurse only into `type:'object'`** properties — never array items. No index (`a[0].b`) or JSONPath-filter (`a[?(@.id==9001)]`) syntax exists on the editable path (only `displayTransformer` runs JSONPath, and that's **display-only**). So **any array whose elements you want individually editable must be reshaped to a keyed object on pull and back to the array on publish** (key it by a **stable, collision-free, path-safe id** — not a renameable label, which churns keys). Examples: **GoHighLevel** `customFields[]` ↔ keyed `custom_fields{shortKey}` (and the keyed object diffs per-field, which fixed a per-field publish bug); **Copper** `custom_fields[{custom_field_definition_id,value}]` ↔ keyed `{cf_<id>: value}` (`gohighlevel/`, `copper/`). (Confirmed in `scratch-desktop` `getByPath`/`setByPath` + `build-column-definitions.ts`, and the Rust CLI `get_by_path`.)
- **Date / number normalization.** The service silently snaps a date to a day/tz boundary or coerces number precision, so the write **doesn't round-trip exactly**. Examples: **ClickUp** `due_date` → day boundary in workspace TZ unless `due_date_time:true` (`clickup/STATE.md`); **Affinity** Date fields are day-granularity — a `10:30Z` write reads back as org-tz midnight (`affinity/STATE.md`).
- **Server-side name/case normalization on create.** A service can silently normalize a field on **create** (most often title-casing a person/company name), so the created value doesn't round-trip byte-exact and the create patch lingers in `files unpublished`. Tell: the value you sent comes back re-cased/trimmed. Example: **Affinity** v1 `POST /persons {first_name:"ZZZ-CLI-P2"}` reads back `"Zzz-cli-p2"` (company name / opportunity name are NOT normalized) (`affinity/STATE.md`). Same phantom-patch family as date-snapping and hydrated-reference reads — `files discard` after confirming in the service.
- **Lossy text encoding (emoji / astral chars).** Some services store text as 3-byte `utf8` (not `utf8mb4`), so BMP unicode survives but **4-byte/astral characters (emoji) are silently replaced with `?`** on write. Tell: accented chars round-trip but `🎯` comes back as `?`. Confirm it's the service (raw API probe), not the connector — and **don't assume; it varies by service**: **Zoho** strips emoji to `?` (3-byte utf8), but **Copper** preserves emoji intact (utf8mb4) across system text, custom String, and array elements. Test it per connector (`zoho/STATE.md`, `copper/STATE.md`, `affinity/STATE.md` — Affinity preserves emoji intact in field values AND person names).

### Write

- **Feature-gated fields fail the whole write.** A field gated on a service add-on/feature; sending it when the feature is off **errors and fails the entire record write** (not just that field). Tell: a 4xx naming a feature/app. Fix: only send a non-null value the user actually set. Examples: **ClickUp** `points` (Sprint Points ClickApp), `time_estimate` (Time Estimates) → `400 ITEM_227` (`clickup/STATE.md`).
- **Silent success that didn't land.** An op reports success but the data isn't there: a per-record create fails under a connection-level "Published", or a `limit`-cap `422` **empties the folder while the job reports OK**. **Always verify each write in the service API and that `files unpublished` is empty.** Examples: **GoHighLevel** per-record create silent-fail; limit-cap silent-empty-pull (`gohighlevel/STATE.md`).
- **Field clears (null-sets) from the CLI are silently dropped — PLATFORM bug, hits every connector.** The CLI's patch dialect is JSON **merge-patch** (`null` = _delete the key_), while the publish plan's `computeChangedFields` **intentionally ignores deleted keys** — so a cleared field yields an empty diff, the record is skipped at dispatch, and the CLI prints "Published". Nested nulls bite too (a sub-key written as `null` can never converge with the stored patch — the file stays "unreviewed" forever; the worktree must _remove_ the key instead). Tell: publish "succeeds" but the service still has the old value, and only null-valued edits are missing. Found on **Affinity** (service itself accepts `data:null` clears fine — verified raw) (`affinity/STATE.md`).
- **Multi-folder publish commits only the FIRST folder's batch to `main` — PLATFORM bug.** One publish touching records in two folders (e.g. a People file + a Companies file) wrote both to the service, but only the first folder got its `Publish V2 edit batch` commit; the second file stayed stale on main/dirty with all ops marked success. Tell: after a multi-folder publish, one file's patch lingers in `unpublished` and main lacks its change while the service has it. Re-publishing the leftover patch alone heals it. Found on **Affinity** (`affinity/STATE.md`).
- **Hydrated reference reads ⇒ phantom pending patches after a successful publish.** When the service stores a reference write (`{id}` / `{dropdownOptionId}`) but reads it back **hydrated** (full person/company object, dropdown text/rank/color, `totalCount` siblings), the user's sparse edit never byte-matches canonical — the CLI's value-based re-anchor keeps the patch pending forever and logs a `conflicts.log` entry even though the write landed. Workaround: `files discard` after confirming in the service. Tell: publish confirmed in the API but the file never leaves `files unpublished`. Example: **Affinity** person/company/dropdown values (`affinity/STATE.md`).
- **Truncated multi-value reads would delete data on write.** Multi-value fields that paginate (`totalCount > data.length`) are truncated on read; writing the truncated array back destroys the unfetched values. Refuse the write when `totalCount` exceeds the array length. Example: **Affinity** `person-multi`/`company-multi`/`filterable-text-multi` (`affinity-write-translation.ts`).
- **FK / relationship modeling.** A relationship can be a **plain id field**, a **separate association endpoint**, or a **relationship custom-field type** — identify which and test that path both directions. Examples: **Copper** plain id field (`primary_contact_id`), **HubSpot** association endpoint, **ClickUp** `tasks`-type custom field (`copper/`, `clickup/`).
- **FK needs a bare-scalar id — a decorated/nested reference can't be declared without reshaping.** `x-scratch-foreign-key` works only when the field's _value_ IS the foreign id (a scalar column, like Copper's `primary_contact_id: <number>`). When the reference reads as a **decorated object** (`{id, name, …}`) or an **array of them**, nested inside a field value, no annotation on that shape produces a working FK (arrays are leaves on the editable path). Tell: the relationship round-trips fine as a value but there's no scalar column to hang the FK on. Two outcomes: declare FKs only on the **clean scalar-id columns** (do that now), and for the decorated/nested refs either reshape `value.data`→keyed-scalar-id on pull (playbook array→keyed-object pattern) or defer it as a design decision. Example: **Affinity** — entity-files `person_id`/`organization_id`/`opportunity_id` are clean scalar FKs (declared), but person/company _field-value_ references are decorated objects → deferred for reshaping (`affinity/STATE.md`, `affinity/PLAN.md`).
- **FK target eligibility (a valid id isn't always an _acceptable_ id).** A relationship field can require the target to satisfy a **service-side eligibility rule**, not just exist — so a write with a real id is still rejected (often a generic `422`/"data integrity" with no field name). Tell: re-parenting to _some_ targets lands and to others fails; a raw-API write reproduces the failure (proves it's the service, not the connector). When you hit it, confirm via the service API directly, then document which targets are eligible. Example: **Copper** `Companies.primary_contact_id` only accepts a person **related/eligible to that company** — a fresh (free) person is accepted and auto-related, but a person already tied to a different company → `422 "Data integrity error"`, failing the whole record (`copper/STATE.md`). The connector still behaves correctly: the failed write stays in `files unpublished` — so the move-to-different-parent FK test must pick an _eligible_ second parent (and `unpublished`-empty, not the CLI "Published" line, is the proof). **Related variant — set-on-create-only FK fields:** some relationship fields are settable on create but the service **silently ignores updates** to them (e.g. **Copper** `Opportunities.company_id` — raw API `PUT` returns 200 with no change). A CLI "move" of such a field is a harmless no-op, not a connector bug; confirm create-vs-update behavior per FK field (`copper/STATE.md`).
- **Cross-field validation breaks sparse (changed-only) updates.** A field can be validated against a _sibling_ field, so updating just one (the connector's sparse `changedFields` path) fails even though the value is fine — you must send the dependent field too. Tell: a `4xx`/`INVALID_DATA` naming a field, that disappears when you include its sibling. Reproduce on the raw API to confirm it's the service. The connector behaves correctly (failed write stays in `files unpublished`); the _test_ just needs to edit both. Example: **Zoho** `Events.Start_DateTime` is validated against `End_DateTime` ("start should be greater than end") — lone-Start update → 400; send Start+End together → OK (`zoho/STATE.md`).
- **Custom-field definitions may be API-creatable even when assumed UI-only — probe before hand-seeding through the browser.** A prior connector's notes (or vendor docs) can say "custom fields are UI-only," but the create endpoint may actually exist; a one-line `POST` probe can replace a long browser-seeding session. Tell: `GET /custom_field_definitions` (or equivalent) exists — try the matching `POST` before opening the field-manager UI. Example: **Copper** `POST /custom_field_definitions` creates every type except `Connect` (UI-only), despite the long-standing "UI-only" assumption (`copper/STATE.md`).
- **Storage / edition caps block ALL creates (test like update instead).** A free/over-quota org can be at a hard **record-count cap**, so every `POST` 4xx's (`MAX_LIMIT_REACHED`) **org-wide** — even a minimal create — while **update/pull keep working**. Tell: minimal create 400s but an existing-record edit succeeds. Don't read it as a connector bug; prove write coverage **non-destructively via `updateRecords` (save-and-restore on an existing record)** and gate create/delete behind an env flag for a green-field org. Example: **Zoho** free-edition 5000-record cap, Accounts at 25k (`zoho/STATE.md`).

- **Split writes across two API versions — and route a field through the _better_ version even when its record was created on the _older_ one.** When a service's newer API covers some writes (e.g. field-value edits) but the older one is needed for others (whole-record create/delete), don't mirror the old API's awkward sub-resource model. Create the record's _basics_ on the old API to get an id, then set its _field values_ through the **new** API — verify the new-API field write works on an old-API-created record (it usually does), and you sidestep the old API's per-element/multi-value endpoints entirely. Example: **Affinity** — v1 `POST /persons|/organizations` for create, then v2 `PATCH /…/fields` for values (proven to work on a v1-created record), avoiding v1's one-row-per-element field-values endpoint (`affinity/STATE.md`, `affinity/ARCHIVE.md`).

### Per-entity & API request quirks

- **Per-entity inconsistency.** The same concept differs **per entity**: value-key, scoping param, pagination style, `limit` cap (docs often wrong — probe the real cap from 100). Don't assume uniformity. Examples: **GoHighLevel** value-key (`value` vs `fieldValue`), location param (`locationId`/`location_id`/query), per-entity pagination & limit caps (`gohighlevel/STATE.md`).
- **Required version/date headers.** A mandatory header on **every** request; omit it → obscure failure. Example: **GoHighLevel** `Version: 2021-07-28` (`gohighlevel/STATE.md`).
- **Pagination cursor leakage.** Pagination tokens are **transport, not data** — strip them from each record before storage so cursors don't leak into the saved JSON. Example: **GoHighLevel** `searchAfter` (`gohighlevel/STATE.md`).

### Schema & structure

- **Static vs dynamic schema sourcing.** Decide per object family **where the schema comes from**: **dynamic** data (user-defined objects/fields — Airtable columns, Notion props, custom fields) → hit the service's **discovery endpoint** at runtime and build the schema from it. **Static** data (fixed system entities/fields the service does **not** expose via any schema/describe endpoint) → **figure the fields out from the API docs / OpenAPI / similar and HARDCODE them** in the connector — this is the sanctioned exception to "discover dynamically" (there's nothing to ask). **If a discovery endpoint already returns the static fields alongside the dynamic ones, use that endpoint for both** (simpler — one path); only hardcode the static schema when it is **not exposed by any endpoint**. Tell: the table view shows only `id` (or a near-empty schema) because the generic builder punted instead of enumerating the fixed fields. Example: **GoHighLevel** — 13 read-only list entities (calendars, products, users, …) have no field-metadata API, so their columns are hardcoded from the published OpenAPI into `GOHIGHLEVEL_ENTITY_FIELDS`; Contacts/Opportunities/Custom-Objects DO have discovery APIs (`customFields`/`getObjectSchema`) and stay dynamic (`gohighlevel/STATE.md`).
- **Schema you can read/set but can't create via API.** Custom fields are readable and value-settable but **UI-only to create** — seed one of each type via the service UI before testing field types. Example: **ClickUp** custom fields (Custom Field Manager) (`clickup/STATE.md`).
- **Structural object modeling.** How the service models sub-objects decides the codepath (and the [path structure](#structural-hierarchy--scratch-folder-paths)): e.g. a **subtask is just a record with a `parent`** (no special path needed), statuses are **per-list not global**. Example: **ClickUp** (`clickup/STATE.md`).
- **A metadata flag that *looks* like a read-only signal but isn't — verify which flag actually gates writes.** A field-metadata payload can carry several boolean-ish flags (`is_system_attribute`, `is_managed`, `editable`, `read_only`, …); picking the wrong one to drive `x-scratch-readonly` either locks writable fields or exposes read-only ones. **Don't infer from the name — pull real attribute metadata and compare a known-writable field against a known-read-only one.** Example: **Attio** — `is_system_attribute` is `true` for nearly every standard field *including writable ones* (`name`/`description`/`domains`), so it's useless as a read-only signal; the precise flag is **`is_writable === false`** (true read-only only for `record_id`, `created_at`, `*_interaction`, `logo_url`, follower counts), present on both object and list attributes (`attio/STATE.md`, `isAttributeReadonly`).

### Identity & auth
- **Nested record-id paths (`idColumnRemoteId` is a dot-path, not a property name).** A connector whose remote id lives inside a nested object (Attio's `id.record_id` triple, list entries' `id.entry_id`) must be read/written **everywhere** with the IdPath helpers (`readRecordId`/`readRecordIdAsString`) or lodash `get`/`set`/`unset` — a plain `obj[idField]` access silently returns `undefined`. Tell: creates publish fine but the record then can't be updated/deleted ("Could not resolve remote ID" while the CLI prints "Published"), no FileIndex row after create, and a later pull re-materializes the record under a new filename. Found+fixed in `publish-plan-run.service.ts` (create/update/delete dispatch) on the first nested-id connector — pull & sync already used the helpers; **when adding a nested-id connector, smoke the full create→edit→delete cycle with no intermediate pull** (`attio/STATE.md`).
- **Filename ≠ id; id lives inside the file.** The filename may be a **name-slug** or the **remote id**; the id is **always inside the file**; new records get their id **after** publish. Examples: **Copper** name-slug, Airtable/Webflow remote id (`copper/STATE.md`).
- **Credential UI quirks.** Masked token fields (copy-only), an SSO re-auth to mint a token, multi-field auth. Examples: **ClickUp** `pk_` token masked + Copy-only + Google SSO re-auth; **Copper** apiKey+email (`clickup/`, `copper/`).
- **Multi-region OAuth (per-region auth/token/API hosts).** A provider split across regions/data centers has **per-region authorize, token, AND API hosts** — pick the region up front (a connect-form field, like Shopify's `shopDomain`), thread it through the OAuth `state`, **persist it** (e.g. `oauthWorkspaceId`) so token _refresh_ and the connector's API calls hit the right region, and **derive the API host from it** (don't hardcode). Three gotchas: (1) the OAuth **client must be registered/enabled in each region** (Zoho: single-DC by default, "Enable Multi-DC" in the API console; may issue a **per-region secret**); (2) **the user-picked region must match the account they authorize** or the code is rejected — and providers may return that as **HTTP 200 with `{error}`** (not a 4xx), so handle both and surface a clear message, not a 500; (3) a region typo gives a cryptic failure, so a **dropdown beats free-text**. Example: **Zoho** US/EU/IN/… — `ZohoOAuthProvider` routes authorize/token/refresh to `accounts.zoho.<dc>` and the API to `zohoapis.<dc>` from a user-selected DC, validated live on US + EU (`zoho/STATE.md`).

## General Scratch / CLI / browser gotchas (apply to every connector)

- **CLI publish is 3 steps:** `files accept` → `files upload` → `files publish`. `linked publish` alone **no-ops yet prints "completed"** (it never uploads the accepted patches). Always upload first.
- **`files upload` needs GCS + valid gcloud creds (local-dev trap).** `upload` → `POST /cli/v1/workbooks/:id/upload-patch/init` issues a **GCS presigned PUT URL** (`object-storage.service.ts`, gated on `GCS_PATCH_UPLOAD_BUCKET`). In local dev the signing uses **impersonated gcloud ADC** (of `GCS_LOCAL_SIGNING_SA`); when those expire you get a **500** on upload with `invalid_rapt` / `SigningError` in the server log. Confirm it's this gate (not the connector) by testing the impersonation directly: `gcloud auth application-default print-access-token --impersonate-service-account=<GCS_LOCAL_SIGNING_SA>` — a refresh error ("Please run gcloud auth login") is the tell. Fix: `gcloud auth login` **and** `gcloud auth application-default login`. **⚠️ Then restart the running server** — a long-lived `yarn dev` / `nest start --watch` process **caches the old ADC in-process** and a gcloud file change does NOT trigger its code-watch restart, so `files upload` keeps 500ing until the node process reloads (touch a server source file to force the watch restart, or restart `yarn dev`). This blocks the publish path for **every** connector — when `files upload` 500s, check the server log for the GCS sign error before suspecting the connector. To prove writes meanwhile, run a **live-API integration spec** (`server/test/integration/<svc>-connector.spec.ts`) that drives the connector's create/update/delete directly and reads back via the service API.
- **Confirm pushes against the service API, not a Scratch pull.** A pull replays still-pending accepted patches over `main`, so the local file can look right while the service is unchanged.
- **`files publish` is 403'd** unless `User.settings.cliCanPublish = true` (web app Settings → Integrations).
- **Read-only fields** (`x-scratch-readonly`: ids, `date_created/modified`, computed) are dropped on publish by design — omit them from new records. But never _silently_ strip a user's edit to a read-only field; let the service reject it.
- **CLI can create connections** only for `user_provided_params` services (`scratchmd connections add --service <S> --param k=v`). **OAuth** services must be connected via the web app's browser flow.
- **Browser ambiguous clicks:** when a toolbar button and a menu item share a name, `$B click` errors "matched multiple elements" — fall back to `$B js` to click the precise DOM node. JS `.click()` also bypasses overlay coverage (e.g. a survey toast over a Save button).
- **Wedged local state** (dirty branch / accepted-patches / SQLite index): don't fight it — `workspaces unsync` + re-`init` + re-`pull`; the service and server git are the source of truth.
- **Same-named folders across two connections collide in publish (was a real bug, fixed 2026-06-05).** If a workbook has two connections that each expose a folder with the same path (e.g. a CRM and a generic-api connection both have `/Contacts`), the publish plan-build used to resolve the DataFolder by path alone and could hand one connector the _other_ connector's schema/table-id — mis-routing writes (a HighLevel contact create went to `POST /objects/GET/records` → 400, silently lost). Fixed by scoping `SchemaHelperService.getDataFolderInfo` by `connectorAccountId`. **When testing a connector in a multi-connection workbook, watch for same-named tables across connections** and confirm writes actually land (the CLI may still print "Published" — DEV-10175). The reliable check after a push: `files unpublished` is empty AND the record carries a remote id AND it's in the service API.
