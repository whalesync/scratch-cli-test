DEV-11316 · scratch-git · plan for MR 2 → 4

Background GC for scratch-git

Unlink repo operations from garbage collection. Compact cheaply and incrementally after every job; run a full, pruning git gc only from a background sweep, on idle repos, one at a time — without giving up pack quality.

MR 1 · !3253 · locks + marker + exit check + prune grace MR 2 · scratch-git detached /gc MR 3 · server client + callers MR 4 · maintenance sweep

1. The shift in one picture

Today every pull and every sync destination ends with a synchronous POST /gc that runs a full git gc — O(entire history), ~12.5 h/day of repack I/O on the box, and the Stripe repo's ~5-minute run sits right on the 300 s proxy cliff. After MR 2–4, jobs make one cheap, bounded call and get on with their lives; the expensive work moves to a sweep nobody is waiting on.

2. Two modes, two very different budgets

The whole design turns on the fact that git's maintenance work splits cleanly into steps that are bounded and safe next to writers and one step that is neither. We use the first kind constantly and the second kind rarely.

mode: compact · the hot path

Pack what's new, keep the pack count small

  • Skip outright when loose < 500 — most publishes end here in ~5 ms.
  • Otherwise one bounded step: pack loose objects (batch-limited), then roll the small packs together geometrically so lookups stay fast.
  • Deletes nothing. Unreachable objects get packed, not dropped → safe while other writers are mid-build. No exclusive lock; the marker just keeps two compacts off the same repo.
  • Cost O(new objects). Kill it mid-way and you lose only that few-second run.
  • Reports done or more_needed from count-objects.
mode: full · the sweep only

Real git gc, with a grace, when idle

  • git gc --prune=1.hour.ago: rewrite all reachable objects into one pack with fresh deltas, prune unreachable objects older than the grace, write commit-graph.
  • The only step that reclaims disk and the one that gives the best deltas + fastest clones.
  • All-or-nothing (temp pack renamed at the end): kill it and nothing was gained. So: detached, never on a request, never behind nginx.
  • Under the repo's exclusive lock; writers wait ≤10 s then get 409 gc_in_progress. Cron only starts it on idle repos, so that 409 is the exception.
  • Runs on already-compacted repos, so it's fast — the 300 s cliff stops mattering.

Choice for compact: the two git maintenance tasks (batch-limited by design, built to run beside other git commands). repack -d --geometric=2 is the alternative to measure on the two big repos; either is fine — the property we need is "bounded, non-deleting, converges over repeats".

3. MR 2 — scratch-git: a GC that isn't a request

The endpoint stays POST /api/repo/manage/{id}/gc, so today's callers keep working. What changes: the run is a detached task that owns its guard and marker; the HTTP call is a window onto it, not its lifetime.

4. MR 3 — server: one choke point for "GC is running"

No per-call-site plumbing. ScratchGitClient.callGitApi learns exactly one new thing: a 409 whose body carries code: "gc_in_progress" means wait, this is transient — and how long to wait depends on who's asking.

  • Callers: pull-linked-folder-files.job.ts, sync-data-folders.job.ts, and — new — publish.job.ts call runGitGc(repo, { mode: 'compact', waitSeconds: 60 }). Publish was the one loose-object producer nobody ever compacted. running/more_needed is a debug log, not an error.
  • Timeouts: per-call AbortSignal.timeout(...) (DEV-11235) so no call ever silently waits the full 300 s.
  • Remove the "409 from /gc means already running, skip" special-casing — /gc now returns 200 already_running.

5. MR 4 — the sweep: cycle repos, bounded steps, done or not

An hourly cron (server/src/cron/git-maintenance.service.ts) that treats the repo itself as the state. It never stores "progress" — count-objects says whether a repo is done, and a repo that isn't goes back in the queue. Crash it anywhere; the next run continues correctly.

6. Where we don't compromise on compaction quality

Incremental ≠ sloppy. The trade is when we pay for the best pack, not whether.

  • Pack count stays logarithmic. Geometric roll-ups (or incremental-repack) mean a repo never drifts into "hundreds of small packs, every lookup checks all of them". Loose objects — the actual bloat and the actual read-performance killer — go to ≈0 continuously.
  • Deltas are recomputed inside every roll-up, so most objects get good deltas soon after they land. What incremental cannot do is cross-pack deltas against the whole history and prune — that is exactly what the periodic full pass is for.
  • Every repo still gets a real git gc — at least every 7 days, sooner if the pack count says so — but on a repo that is already compact, so it is fast, and idle, so it costs nobody a wait.
  • Disk is reclaimed by full only, with a 1 h grace (env-tunable, now refused). Garbage a few hours old is not the disk problem (DEV-11253's is loose objects and unswept staging), so the grace costs nothing measurable.
  • Bitmaps: git gc writes a bitmap index by default — a big share of full-repack cost and only clones benefit. Decision to take with the first measurements: repack.writeBitmaps=false for hot repos.

7. Open decisions (small, measure-then-choose)

  1. compact = maintenance loose-objects + incremental-repack vs repack -d --geometric=2. Lean geometric; measure on Stripe + the incident repo first.
  2. Thresholds: L loose (500 for hot-path skip, 5 000 for sweep candidacy), P packs (≈20–50), full-GC age (7 d).
  3. Worker retry budget 5 min vs 2 min — after compaction a full GC on the Stripe repo should be well under either.
  4. GET /gc history in memory + logs (v1) vs persisted lastFullGcAt column.
