# Context

This folder contains implementation and design plans that are generated by agents for review or future implementation.

# Layout: one folder per plan

Each plan lives in its own folder, and the plan markdown file inside repeats the folder name:

```
docs/plans/<YYYY-MM-DD>-<slug>/<YYYY-MM-DD>-<slug>.md
```

For example: `docs/plans/2026-06-27-design-exploration/2026-06-27-design-exploration.md`.

Repeating the descriptive name on the markdown file (rather than a generic `plan.md`) keeps editor tabs, fuzzy-finder results, and grep output unambiguous when many plans are open at once.

The folder gives each plan a home for companion artifacts — HTML design mockups, screenshots, diagrams, sample data — that belong with the plan. Drop them alongside the markdown file in the same folder.

The grouping subfolders (`resolved/`, `cancelled/`, `integration-tests/`) hold plan folders too, with the same `<slug>/<slug>.md` shape inside them.

# Guidelines for plans

- Plans should include the timestamp when they are first created in YYYY-MM-DD format
- Include a status field with one of the following values:
  - Planned
  - In Review
  - In Progress
  - Resolved
  - Cancelled
- Plans should be attributed to the author that is generating the plan
  - utilize their git user name
- Plans should have a status property
- Link to a linear task when possible, prompt the user for one when generating the plan

# Resolving Plans

Once a plan is fully implemented its entire folder should be moved into the `resolved` folder (e.g. `git mv docs/plans/<slug>/ docs/plans/resolved/`), carrying any companion artifacts with it.

- Plans should not be long-term documentation and will eventually be deleted
- Prompt the user ifthey need to create new documentation for the change:
  - that are summaries of the change
  - The user who initially generated the plan use git username
  - problem statement
  - key decisions made
  - diagrams related to the system or infrastructure
  - any relevant operation examples like setup and examples
