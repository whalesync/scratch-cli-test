Background GC for scratch-git

Unlink repo operations from garbage collection. One bounded, non-deleting step after every job — hard-capped at 30 seconds. Everything expensive moves to a sweep that runs incrementally, outside any request, while the repo keeps taking reads and writes.

MR 1 · !3253 · locks + marker + exit check + prune grace plan · !3254 MR 2 · scratch-git detached /gc + freshen-on-write MR 3 · server client + callers MR 4 · maintenance sweep

1. The two guarantees

Everything in this plan exists to make two statements true. Each is checkable on its own, and each names the mechanism that makes it true.

G1
After a pull, sync or publish, the job runs one GC step that finishes in ≤ 30 s regardless of repo size — and never waits longer. mode: compact packs at most batchSize loose objects and deletes nothing. The bound is a wall-clock budget (budgetSeconds, default 30) that kills the git child — not an object count, because on this workload time is not a function of count (§3). Every step is crash-safe, so a kill costs only that step's work; the job reads more_needed or timed_out and moves on.
G2
Maintenance runs outside any request, incrementally, and the repo keeps serving reads and writes while it runs. An hourly sweep applies bounded steps — compact, geometric roll-up, and a rare full git gc --prune=1.hour.ago — with no exclusive lock. Reads were never blocked (git repacks atomically; gix re-reads its pack list on a miss). Writes stop being blocked once scratch-git freshens objects it re-writes — the one piece of git's own writer-versus-GC concurrency model that gix skips today (§4). Until that is proven in production, the exclusive lock stays behind a flag.

2. The shift in one picture

Today every pull and every sync destination ends with a synchronous POST /gc that runs a full git gc — O(entire history), ~12.5 h/day of repack I/O on the box, and the Stripe repo's ~5-minute run sits right on the 300 s proxy cliff. Publish, the biggest loose-object producer, never calls GC at all. After MR 2–4, jobs make one capped call and get on with their lives; the expensive work moves to a sweep nobody is waiting on.

4. Why full GC needs no lock — git's model, and the one gap in gix

git is designed to run gc next to live writers. Its rule has two halves:

  1. GC deletes only unreachable objects older than the grace (mtime of the loose file, or of the pack that holds it — F4c/F4d).
  2. A writer that re-uses an existing object freshens it — write_object_file in git calls freshen_packed_object / freshen_loose_object instead of writing, which updates the mtime. So anything a write is about to reference is younger than the grace when the ref moves.

Half 1 arrived in MR 1 (--prune=1.hour.ago). Half 2 is missing: gix::Repository::write_object_inner (gix 0.70) does if self.objects.exists(&oid) { return Ok(..) } — no write, no touch. That is the only reason the 2026-08-18 plan put full under an exclusive lock: an abandoned dirty snapshot's object, older than an hour, re-used by a new write, could be dropped by repack -A between the writer's exists-check and its ref update.

Fix (MR 2, scratch-git): route the five write_object call sites (git/repo.rs ×3, git/rebase.rs ×2) through a helper that never skips: when the object exists, still call objects.write_buf. gix-odb's loose writer renames a temp file over the existing path (finalize_object → persist), so a loose object gets a fresh mtime and a pack-only object gets a fresh loose copy. Either survives gc: prune-packed only removes loose objects present in a remaining pack, and prune only removes old ones.

Invariant, and where it is checked

Every object a write references is either reachable at that instant, or was written/freshened by that write within the grace.

  • Commits, trees, blobs built by pull/sync/publish/rebase: written via the helper → freshened. Untouched subtrees are referenced by id from the previous main/dirty commit → reachable.
  • Staged uploads: plain files under {staging_dir}/{jobId}, turned into objects at commit_staged time → written then.
  • Tags (write_tag) point at commits that are reachable from a branch.
  • Anything found to hold an object unreferenced for longer: raise SCRATCH_GIT_GC_PRUNE_EXPIRY to 1.day.ago. Disk cost is negligible — DEV-11253's bloat is loose objects and unswept staging, not garbage.

5. Three steps, three budgets

git's maintenance work splits into steps that are bounded and non-deleting — usable constantly, under nothing more than the per-repo marker — and one step that reclaims disk and rewrites history's deltas. We use the first kind on the hot path and in the sweep, and the second kind rarely.

compact · hot path + sweep

Pack a batch of loose objects

  • count-objects; if loose < looseThreshold (500) → skipped in ~5 ms. Most publishes end here.
  • Else enumerate ≤ batchSize (5 000) loose ids → git pack-objects -q objects/pack/loose- on stdin → git prune-packed -q.
  • Deletes nothing. Unreachable loose objects get packed, not dropped.
  • Hard budget 30 s: child killed → timed_out. pack-objects writes tmp_pack_* and renames at the end, so a kill leaves the repo unchanged; the sweep removes tmp_pack_*/tmp_idx_* older than 1 h.
  • Returns done / more_needed from the after-count.
rollup · sweep only

Keep the pack count logarithmic

  • git repack -d --geometric=2 --write-midx: packs below the ×2 split roll into one; nothing is dropped (F4a).
  • Deltas are recomputed inside every roll-up → good deltas soon after objects land.
  • Not on the hot path: a roll-up can be large (108 s for 30 000 objects here). Budget 600 s in the sweep — nobody waits.
  • Marker only. Repo stays readable and writable.
full · sweep, rarely

Real git gc with a grace

  • git -c repack.writeBitmaps=false gc --prune=1.hour.ago: one pack with cross-history deltas, prune old garbage, commit-graph.
  • The only step that reclaims disk. All-or-nothing → detached, never on a request.
  • When: compact ∧ (packs ≥ P ∨ last full > 7 d). On an already-compact repo it is fast.
  • Lock-free per §4; exclusive only while the flag is on. flock on the repo dir so blue/green never run two.
  • Leaves young unreachable objects loose (F4b) — expected, compacted next visit.

7. MR 3 — server: callers and one choke point

  • Callers: pull-linked-folder-files.job.ts:510, sync-data-folders.job.ts:471, and — new — publish.job.ts call runGitGc(repo, { mode: 'compact', budgetSeconds: 30, waitSeconds: 60 }). Publish was the one loose-object producer nobody ever compacted. more_needed / timed_out is a debug log, not an error; failed is a warning with a metric. The existing "409 from /gc means already running, skip" special-casing goes: /gc now returns 200 already_running.
  • Timeouts: per-call AbortSignal.timeout(...) in callGitApi (DEV-11235) so no call ever silently waits the full 300 s.
  • 409 gc_in_progress by role — only reachable while SCRATCH_GIT_FULL_GC_EXCLUSIVE=true: worker → sleep 10 s × N up to SCRATCH_GIT_GC_WAIT_BUDGET_MS (5 min); api → ScratchGitConflictError → 409 "Connection is being maintained, retry shortly". One place, no per-call-site plumbing. Dormant after MR 5.

8. MR 4 — the sweep: cycle repos, bounded steps, done or not

An hourly cron (server/src/cron/git-maintenance.service.ts, registered in cron-job-definitions.ts + runnerBySlug) that treats the repo itself as the state. It never stores "progress" — count-objects says whether a repo is done, and a repo that isn't goes back in the queue. Crash it anywhere; the next run continues correctly. Because compact and roll-up are non-locking, the sweep does not need the repo idle; the idle gate (no running DbJob / RoutineRun on the workbook) applies to full only while the exclusive flag is on, and afterwards only as a courtesy to avoid I/O contention with a publish.

9. Where we don't compromise on compaction quality

Incremental ≠ sloppy. The trade is when we pay for the best pack, not whether.

  • Pack count stays logarithmic. Geometric roll-ups mean a repo never drifts into "hundreds of small packs, every lookup checks all of them". Loose objects — the actual bloat and the actual read-performance killer — go to ≈0 continuously.
  • Deltas are recomputed inside every roll-up, so most objects get good deltas soon after they land. What incremental cannot do is cross-pack deltas against the whole history and prune — that is exactly what the periodic full pass is for.
  • Every repo still gets a real git gc — at least every 7 days, sooner if the pack count says so — but on a repo that is already compact, so it is fast, and lock-free, so it costs nobody a wait.
  • Disk is reclaimed by full only, with a 1 h grace (env-tunable, now refused). Garbage a few hours old is not the disk problem.
  • Bitmaps off (repack.writeBitmaps=false): a large share of full-repack cost; only clones benefit, and desktop clones of these repos are rare.

10. Open decisions (small, measure-then-choose)

  1. batchSize default 5 000 vs adaptive (halve after a timed_out, double after a fast done). Start fixed; add adaptation if kills show up in the metric.
  2. Thresholds: looseThreshold 500 for the hot-path skip, L 5 000 for sweep candidacy, P ≈ 20–50 packs, full-GC age 7 d.
  3. When to flip SCRATCH_GIT_FULL_GC_EXCLUSIVE: one week of clean fsck canaries after freshen-on-write is live, or longer if any full ran under the flag with a writer queued.
  4. Grace 1.hour.ago vs 1.day.ago: raise if any write path is found to reference an object it neither wrote nor freshened within the hour.
  5. GET /gc history in memory + logs (v1) vs a persisted lastFullGcAt column.
