# Scratch Scenario Tests

End-to-end tests that exercise the full Scratch workflow against real services. No mocks. The input is API responses from connections. The output is API responses from connections. Everything in the middle is implementation details.

## What This Tests

Pull content from real Airtable → Scratch CLI creates workspace, links tables, configures syncs → sync transforms records → publish pushes to real WordPress → curl WordPress REST API to assert results.

The tests are **codebase agnostic** — they don't care whether the engine is Python, Rust, or NestJS. They test what the tool does for customers. If the implementation changes, these tests don't.

## Architecture

```
.env                          # Credentials (gitignored)
setup.py                      # Phase 0: CLI-based workbook setup
run.sh                        # Test runner (phases 0-4)
assert-wordpress.sh           # curl WP REST API → diff against expected JSON
assert-airtable.sh            # curl Airtable API → diff against expected JSON
assert-supabase.sh            # curl Supabase API → diff (not yet configured)
modify-airtable.sh            # Phase 3: edit source records
restore-airtable.sh           # Phase 4: revert edits
reset/wordpress.sh            # Delete all WP content before first sync
reset/supabase.sh             # Truncate Supabase tables (not yet configured)
expected/wordpress.json       # Expected WP state after sync (phases 1, 2, 4)
expected/wordpress-after-edits.json  # Expected WP state after phase 3 edits
setup-airtable.py             # One-time: create Airtable base (5 tables, 16 records)
enrich-airtable.py            # One-time: add workflow columns + 44 more records
add-attachments.py            # One-time: upload 2 PDFs + 1 CSV to records
```

## Test Phases

| Phase | What happens | What it proves |
|-------|-------------|----------------|
| **0 — Setup** | CLI creates workspace, adds Airtable + WordPress connections, links tables, creates syncs, pulls from Airtable | CLI can set up a complete workspace from scratch |
| **1 — First sync** | Reset WordPress → sync all → publish → assert | Creates, foreign keys, and field mapping work |
| **2 — Idempotency** | Pull → sync → publish → assert (same expected) | Re-running with no changes produces no side effects |
| **3 — Edits** | Modify 3 Airtable records → pull → sync → publish → assert | Updates propagate correctly |
| **4 — Restore** | Revert Airtable changes → pull → sync → publish → assert | System returns to original state |

## Prerequisites

- `scratch` CLI built and on PATH (`scratch-engine/crates/scratch-cli`)
- scratch-ui running locally (default: `http://localhost:8000`)
- scratch-git-2 running locally (default: ports 3100 + 3101)
- `jq` installed
- `.env` file with credentials (see below)

## .env File

```bash
# Airtable
AIRTABLE_TOKEN=pat...
AIRTABLE_BASE_ID=app...
AIRTABLE_TAGS_TABLE_ID=tbl...
AIRTABLE_AUTHORS_TABLE_ID=tbl...
AIRTABLE_POSTS_TABLE_ID=tbl...
AIRTABLE_PAGES_TABLE_ID=tbl...
AIRTABLE_PRODUCTS_TABLE_ID=tbl...

# WordPress
WP_URL=https://your-site.example.com
WP_USER=admin
WP_APP_PASSWORD="xxxx xxxx xxxx xxxx xxxx xxxx"  # quote if spaces

# Scratch API
SCRATCH_API_URL=http://localhost:8000
```

The Airtable record IDs (`REC_TAG_FOOD=rec...`, etc.) are also in `.env`, generated by `setup-airtable.py`. They're used by `modify-airtable.sh` and `restore-airtable.sh`.

## Running

```bash

```

## Airtable Data (Source)

60 records across 5 tables, created by `setup-airtable.py` + `enrich-airtable.py`:

| Table | Records | Notable fields |
|-------|---------|----------------|
| **Tags** | 10 | Name |
| **Authors** | 4 | Name, Email, Bio (rich text) |
| **Posts** | 15 | Title, Body (rich text), Tags (FK), Author (FK), Featured Image, Client Draft, SEO Description, Status |
| **Pages** | 6 | Title, Body (rich text), Parent Page (FK) |
| **Products** | 25 | Name, Description, Price, Images, Tags (FK), Supplier Description, SKU, Category, Status |

**Workflow columns**: Posts have `Client Draft` (raw input) and `Body` (cleaned). Products have `Supplier Description` (raw) and `Description` (cleaned). Only the cleaned columns sync — this matches real customer workflows (pSEO, content prep, raw-input-to-clean-column).

**Attachments**: 2 PDFs + 1 CSV attached to specific records. Ready for when attachment handling is implemented — no setup changes needed, just update the sync/assert code.

## WordPress Setup (Destination)

- WordPress instance with REST API enabled
- Classic Editor plugin active
- SCF (Secure Custom Fields) plugin active with two field groups:
  - **Post Fields**: `seo_description` (text) — "Show in REST API" enabled
  - **Product Fields**: `price`, `sku`, `color`, `weight`, `dimensions`, `in_stock`, `rating`, `product_category`, `supplier_description` — all shown in REST API
- Application Password created for REST API auth

## Sync Mappings

Three syncs configured by `setup.py`:

**Tags → Categories**
- `Name` → `name`
- `Name` → `slug` (slugify transformer)

**Posts → WordPress Posts**
- `Title` → `title`
- `Body` → `content`
- `Title` → `slug` (slugify)
- `SEO Description` → `excerpt`

**Pages → WordPress Pages**
- `Title` → `title`
- `Body` → `content`
- `Title` → `slug` (slugify)

## CLI Commands Used

`setup.py` exercises these CLI commands:

```bash
scratch workspace create --name "Scenario Test"
scratch connection add --service AIRTABLE --param apiKey="$AIRTABLE_TOKEN"
scratch connection add --service WORDPRESS --param endpoint="$WP_URL" --param username="$WP_USER" --param password="$WP_APP_PASSWORD"
scratch connection tables <conn-id>
scratch table add <conn-id> --table Tags
scratch sync create --name "Tags → Categories" --config syncs/tags-categories.json
scratch pull
scratch sync run --all
scratch publish
```

If a command doesn't exist or fails, the test fails — which surfaces the gap immediately.

## Assertions

`assert-wordpress.sh` fetches from the WP REST API and compares against expected JSON:

- **Categories**: name, slug, count (excluding default "Uncategorized")
- **Posts**: title, slug, categories (by slug), has_featured_image, acf fields, status
- **Pages**: title, slug, has_parent, acf fields, status

All results are sorted by slug for stable comparison. Diff output shows exactly what's different.
