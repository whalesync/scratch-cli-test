## Gotchas
- (connector-specific operational notes)
- **Views (DEV-11136):** views are listed alongside tables and usable as a **read** source. A view is enabled when one of its output columns **provably originates from** a single-column-unique base-table column: the view's defining query (`pg_get_viewdef`) is probed with a zero-row `SELECT … LIMIT 0` and the result-row descriptor's origin fields (`resorigtbl`/`resorigcol`, exposed as `result.fields[].tableID/columnID` by the pg driver) give the exact base column per output column — aliased or computed columns can't be mis-attributed, and stacked views are followed iteratively (depth cap 8). That column becomes `idPath` and is marked read-only. What this still can't prove is row-level uniqueness of the view itself — a fan-out join can repeat a PK-backed column's values. Views with no unique-backed column are listed **selectable with `requiresIdFieldSelection: true`** (plus an `infoNote`): the user must choose an ID column at folder-add time (`CreateDataFolderDto.idFieldOverride`), and the spec carries a matching `idPathRequiresUserSelection` marker that `DataFolderService.createFolder` enforces (creation without the override is rejected; pull/schema-refresh re-derivations clear the marker via the stored override or fail loudly if it's gone). Because provenance can't rule out a fan-out join repeating a unique base column, **view pulls carry a runtime duplicate-id guard**: rows arrive ordered by the id column, so duplicates are adjacent and one carried value detects them — a bad view fails the pull loudly instead of silently collapsing records. Creates are always disabled for views; columns of non-updatable views come back `is_updatable = NO` and are marked read-only, so simple auto-updatable views stay editable/publishable. **Materialized views** are discovered via a `pg_class relkind='m'` union (information_schema skips them), with columns synthesized from `pg_attribute`; they're enabled read-only exactly when they carry a single-column unique index (the REFRESH CONCURRENTLY prerequisite), otherwise disabled with a matview-specific reason. FK annotations are not propagated through views. QA fixtures live in the burner project's `fable_qa` schema: `authors_simple_view` (updatable, PK exposed), `bios_with_author_view` (join, read-only, unique id), `author_stats_view` (aggregate, no id), `types_no_pk_view` (updatable, PK hidden), `alias_trap_view` (non-unique column aliased to `id` — must stay disabled), `stacked_authors_view` (view over view), `fanout_types_per_author_view` (join fan-out — enabled statically, pull must fail via the guard), `authors_matview` (materialized + unique index — enabled read-only), `types_matview` (materialized, no index — disabled).
- The FK annotation carries two forms of the target: `linkedTableId`, a display string that drops a `public.` prefix (`authors`, `taxonomy.categories`), and `linkedTableRemoteId`, the linked table's full remote id `[projectRef, schema, table]` — which keeps `public` so it deep-equals that table's `DataFolder.tableId` and can be matched by array equality.
