## Gotchas
- **Field-value canonicalizers — representation churn (DEV-10556).** A SQL store returns what it was given for most columns, but re-renders three families on read-back: timestamps (`timestamptz`/`timestamp` → the driver's `…27.000Z` vs a source's `…27Z`/`…27+00:00`), floats (`0.30000000000000004` vs `0.3`) and `json`/`jsonb` (key order / whitespace). The shared `pg-common/pg-field-value-canonicalizer.ts` (registered as `resolveFieldValueCanonicalizer` since DEV-11420; the sync consults it for every user now that the rollout flag has been removed) compares `TIMESTAMP` columns as instants at millisecond precision (a `date` column, told apart by `format: 'date'`, by the calendar date Postgres stores: the literal date of the written value, time of day and offset dropped), `NUMERIC` at 15 significant digits, `NUMERIC_STRING` (numeric/decimal/bigint strings, DEV-10777) as normalised decimal text — never through a float, so bigints differing beyond float64 precision stay different — and `JSONB` as parsed values; text/boolean/array columns compare structurally. `date` and naive `timestamp` pull the same on every host (DEV-12576, `pg-common/pg-temporal-type-parsers.ts`, per-connection node-postgres parsers): `date`/`date[]` stay the driver's verbatim `YYYY-MM-DD` (a scalar `date` is typed `format: 'date'`; `date[]` stays a plain string array); `timestamp`/`timestamp[]` parse as UTC wall-clock. Before that, the driver's local-time parse made a non-UTC server store `2026-05-01T07:00:00.000Z` for a `date` of `2026-05-01`, so every dated record re-published each run (invisible in production, which runs in UTC). See `pg-common/__tests__/pg-field-value-canonicalizer.spec.ts` and [CONNECTOR_GUIDE → Field Value Canonicalizers](../../CONNECTOR_GUIDE.md#field-value-canonicalizers-diff-stability).
- (connector-specific operational notes)
- **Connection security (DEV-12390, shared with Postgres).** Connection-string mode goes through the same node-postgres allowlist as Postgres (`SupabaseAuthParser` on create, `KnexPGClient` on every connect; see the Postgres `STATE.md`), and every Supabase connection, OAuth project roles included, connects through the database host guard (`SsrfSafeSocket`) in deployed environments. Pooler hosts are public, so OAuth connections are unaffected. Since DEV-12575, `sslmode` is read with libpq meanings and a string with none is encrypted without checking the certificate (what the connector already forced with `sslmode=no-verify`); see the Postgres `STATE.md`. Supabase's form has no certificate fields, so TLS failure messages don't mention them.
- **Exact native column types in Live Export (DEV-11903, shared with Postgres).** The read side annotates every column with `x-scratch-native-column-type: { typeSystem: 'postgres', type, isRecreatableVerbatim }`, where `type` is the exact `format_type(atttypid, atttypmod)` spelling (`integer`, `text[]`, `numeric(12,2)`, `character varying(50)`), read from the catalog join in `KnexPGClient.findAllColumnsInTable`. When a Live Export targets a Postgres-type-system destination (Postgres or Supabase — `POSTGRES_SCHEMA_CREATION_CAPABILITIES.nativeTypeSystem`), the plan carries each recreatable type as `CreateFieldSpec.nativeFieldType`, keeps the source column names verbatim, and `pg-create-schema.ts` creates the column with that exact type. Recreatable = a built-in (`pg_catalog`) type in the allowlist of `pg-common/pg-native-column-type.ts` whose pulled value writes back unchanged; `bytea` (pulled as Node's `{type:'Buffer',data}`), `interval`, enums/domains/extension types and `json[]`/`jsonb[]` fall back to the logical mapping. The same predicate gates `specificType` on create, so a client-supplied native type can never inject DDL. Cross-service sources get the richer logical types instead: an array of primitives becomes a list column (`text[]`/`integer[]`/`boolean[]`, `fieldType.isArray`) and an object a `jsonb` (`json` kind). Any other array (e.g. of objects) still flattens to text: a `jsonb` column declares no shape, so the sync's transform picker would join an array into one string before writing it. Inserts send an ARRAY bound for a `json`/`jsonb` column as its JSON text (`pg-json-column-insert-serialization.ts`, applied via the shared `prepareRecordsForPgInsert`) — the driver otherwise binds a JS array as a pg array literal, which is invalid JSON; strings and objects insert exactly as before. Covered end-to-end against a real database in `server/test/integration/postgres-native-column-types.spec.ts`.
- **Per-project roles are provisioned lazily (DEV-11875).** An OAuth Supabase token authorizes the *Management* API, not Postgres, so reading or writing a project's rows needs a database role Scratch creates itself (`whalesync_svc_…` — named for the company the customer recognizes, since the role lives in *their* database; roles created before that rename keep their old `scratch_svc_…` name and keep working, so the prefix is not a reliable way to enumerate them — via the Management API's SQL endpoint, which runs as the project's `postgres` superuser). That used to happen for **every project in the organization the moment the OAuth callback landed** — connecting one project left a Scratch role sitting in every other one, production databases included, which users (rightly) found offensive. Now the OAuth callback does no Supabase-specific work at all, and a role is created the first time a project is genuinely **used**: a folder added (`fetchJsonTableSpec`), rows read/written, a table or field created. Consequences worth knowing: (a) the project list is read **live** from the Management API on every listing rather than frozen into the credentials at connect time, so a project created or renamed after connecting shows up without reconnecting, and only `ACTIVE_HEALTHY` projects are listed; (b) `credentials.supabaseProjects` now holds **only the projects that have been used**, and grows over time; (c) **browsing must not provision**, so `listTables` / `listCreateDestinations` for an unprovisioned project run their catalog queries through the Management API (`SupabaseManagementApiCatalogReader`) using the same SQL text `KnexPGClient` runs (shared via `pg-common/pg-catalog-queries.ts`); (d) the **one** discovery input that has no Management-API equivalent is the view-provenance probe, which reads the wire protocol's row descriptor — so **views in a not-yet-used project are listed with `requiresIdFieldSelection`** (the supported "name the ID column" path) and regain full analysis once the project is provisioned; (e) two workers can race to provision the same project — each creates a role, the persist step serializes on the connection's credential lock, and the loser adopts the winner's entry and drops its own role. `testConnection` for an OAuth connection with no project in use yet checks the Management API alone.
- **Views (DEV-11136):** views are listed alongside tables and usable as a **read** source. A view is enabled when one of its output columns **provably originates from** a single-column-unique base-table column: the view's defining query (`pg_get_viewdef`) is probed with a zero-row `SELECT … LIMIT 0` and the result-row descriptor's origin fields (`resorigtbl`/`resorigcol`, exposed as `result.fields[].tableID/columnID` by the pg driver) give the exact base column per output column — aliased or computed columns can't be mis-attributed, and stacked views are followed iteratively (depth cap 8). That column becomes `idPath` and is marked read-only. What this still can't prove is row-level uniqueness of the view itself — a fan-out join can repeat a PK-backed column's values. Views with no unique-backed column are listed **selectable with `requiresIdFieldSelection: true`** (plus an `infoNote`): the user must choose an ID column at folder-add time (`CreateDataFolderDto.idFieldOverride`), and the spec carries a matching `idPathRequiresUserSelection` marker that `DataFolderService.createFolder` enforces (creation without the override is rejected; pull/schema-refresh re-derivations clear the marker via the stored override or fail loudly if it's gone). Because provenance can't rule out a fan-out join repeating a unique base column, **view pulls carry a runtime duplicate-id guard**: rows arrive ordered by the id column, so duplicates are adjacent and one carried value detects them — a bad view fails the pull loudly instead of silently collapsing records. Creates are always disabled for views; columns of non-updatable views come back `is_updatable = NO` and are marked read-only, so simple auto-updatable views stay editable/publishable. **Materialized views** are discovered via a `pg_class relkind='m'` union (information_schema skips them), with columns synthesized from `pg_attribute`; they're enabled read-only exactly when they carry a single-column unique index (the REFRESH CONCURRENTLY prerequisite), otherwise disabled with a matview-specific reason. FK annotations are not propagated through views. QA fixtures live in the burner project's `fable_qa` schema: `authors_simple_view` (updatable, PK exposed), `bios_with_author_view` (join, read-only, unique id), `author_stats_view` (aggregate, no id), `types_no_pk_view` (updatable, PK hidden), `alias_trap_view` (non-unique column aliased to `id` — must stay disabled), `stacked_authors_view` (view over view), `fanout_types_per_author_view` (join fan-out — enabled statically, pull must fail via the guard), `authors_matview` (materialized + unique index — enabled read-only), `types_matview` (materialized, no index — disabled).
- The FK annotation carries two forms of the target: `linkedTableId`, a display string that drops a `public.` prefix (`authors`, `taxonomy.categories`), and `linkedTableRemoteId`, the linked table's full remote id `[projectRef, schema, table]` — which keeps `public` so it deep-equals that table's `DataFolder.tableId` and can be matched by array equality.
- **`remoteWebUrl` deep link ("View in Supabase"):** `fetchJsonTableSpec` emits `https://supabase.com/dashboard/project/<projectRef>/editor/<relationOid>?schema=<schema>`. The dashboard's table editor addresses a relation by its Postgres **`pg_class` OID**, never by name — the same id Supabase's own pg-meta emits (`c.oid :: int8 AS id`) — so the connector resolves it with `KnexPGClient.findRelationOidAndKind`, which rides along in the existing `Promise.all` and doubles as the is-this-a-view check the view fallback used to make with a second query. Views and materialized views deep-link the same way. Two guards: the URL is omitted when the relation is missing from the catalog, and (in connection-string mode) when the host isn't `*.supabase.com`/`*.supabase.co` — a self-hosted Supabase or plain Postgres has no dashboard, and the "ref" extracted from its connection string would be meaningless. An OID is **not** stable across a drop/recreate of the relation; that's tolerable because the spec is refetched on every pull, so a stale link self-corrects and in the meantime only lands on the editor's not-found page rather than on some other table.
- **Create-destination deep link (Live Export):** `buildCreateDestinationRemoteWebUrl` emits the same editor URL minus the OID — `.../editor?schema=<schema>` (`buildSupabaseSchemaEditorUrl`) — which lands on that schema's table list, i.e. exactly where the tables we create will appear. It reuses `resolveCreateParent` so `"ref/schema"` and a bare `"ref"` (schema defaulting to `public`) normalize the same way the create path normalizes them, and it is gated on the same `supabaseDashboardDeepLinksAreAvailable` cloud-host check as the per-table link. The "New schema" destination gets **no** link — the schema doesn't exist yet and its name isn't decided until the create runs.
- **"New schema" create destination (DEV-11396):** every project advertises a `created: false` destination that means "provision a schema for this export", so a Live Export doesn't have to drop its tables into a schema that already has another purpose. Its label is `"New schema in <project>"` in OAuth mode and a bare `"New schema"` in connection-string mode — deliberately **not** the sibling `"<project> / <schema>"` shape, which rendered as `"my-project / New schema"` and read like an existing schema that happened to be named "New schema". The label carries no "will be created" wording: `created: false` already says that and the client renders it as a badge. Its id is `"<projectRef>/scratch-new-schema-sentinel-longer-than-any-postgres-schema-name-can-be"` — the segment is deliberately **longer than Postgres' 63-byte identifier limit**, so no schema a user actually has can collide with the sentinel and be silently shadowed by it. `createTable` folds the request's `newParentName` (the user's answer to the "name it" box, or the server's `"<Source service> export"` suggestion) into a snake_case identifier via `foldNameToPostgresSchemaIdentifier` — `Airtable export` → `airtable_export`, defaulting to `scratch_export` — then `CREATE SCHEMA IF NOT EXISTS`. "New" means new: when the folded name is already a schema (any schema, read from `pg_namespace` so system schemas and ones our role can't see count too), `pickUnusedPostgresSchemaName` suffixes it — `postgresql_export` → `postgresql_export_2` — rather than dropping this export beside an earlier one's tables. The chosen name is memoized on the connector instance, so every table in a batch lands in the schema the first one made (`CREATE SCHEMA IF NOT EXISTS` then finds it); the schema actually used comes back as `CreateTableResult.remoteParentId`, and materialize persists that pin the moment the first table reports it so a retry targets the same schema instead of picking `_3`. `resolveRemoteParentIdTheCreateWillLandIn` runs the same choice for plan-from-folder, so the plan sees the new, empty schema and never renames tables against an earlier export's. The plan takes `newParentName` when the client sends it and otherwise derives the same `"<Source service> export"` suggestion materialize falls back to. Residual window: a crash between `CREATE SCHEMA` and that first pin leaves an orphan schema and the retry picks the next suffix. In **OAuth mode** the schema is created by the project's `postgres` role through the Management API, in the same transaction as the table, and the data role is granted USAGE plus default row access on it (DEV-12084, next gotcha). Creating a schema over a *data role* — connection-string mode, and OAuth's fallback — needs CREATE on the **database**, which is broader than the per-schema `GRANT ALL ON SCHEMA` the setup script used to hand the data role — so `buildCreateUserSQL` also issues `GRANT CREATE ON DATABASE current_database()`. **An OAuth connection authorized before that grant landed only needs it if it falls back, and must reconnect then** (setup re-runs and provisions a fresh role with the grant). A `42501` on the data-role statement is translated into mode-appropriate advice — reconnect (OAuth) vs. widen the role in your connection string (connection-string mode) — rather than surfacing a bare "permission denied for database postgres". The REST layer sorts `created: false` first and names it in `CreateDestinationList.defaultDestinationId`, so the picker is *told* to preselect it; nothing about the sentinel lives in a frontend. In **connection-string mode** (one project) that default is always emitted; in **OAuth mode with several projects** there is one "New schema" per project, so no default comes back — picking the project is the user's call, not a coin flip.
- **OAuth Live Export DDL runs as the project's `postgres` role (DEV-12084).** Running `CREATE SCHEMA` / `CREATE TABLE` / `ALTER TABLE … ADD COLUMN` over our data role made that role the owner of everything a Live Export created in the customer's database; a customer (VITL) wanted their own tooling to own the schema, with our role only reading and writing. An OAuth token authorizes the Management API, not Postgres, so the closest thing to "the user's own role" is `POST /projects/{ref}/database/query`, which runs as `postgres` — the owner the dashboard and `supabase db push` use. Mechanics:
  - `SupabaseManagementApiDdlExecutor` sends **one request per create**, wrapped in `begin; … commit;` so a refused statement rolls everything back: the `CREATE TABLE`, one `ALTER TABLE … ADD CONSTRAINT` per foreign key, and `grant select, insert, update, delete on table … to <data role>`. A "New schema" create also carries `create schema if not exists`, `grant usage on schema`, and `alter default privileges in schema … grant select, insert, update, delete on tables to <data role>` in the same transaction. `createFields` sends one request per field, and none for a field that is skipped. Foreign-key targets are still resolved over the data role.
  - The DDL text comes from the same `pg-create-schema.ts` builders, rendered by `pg-common/pg-create-schema-standalone-sql.ts` through a connection-less knex carrying the live client's identifier hooks. Each compiled statement goes through knex's formatter rather than being sent as compiled, because `.toSQL()` keeps knex's `\?` escape (a column named `Featured?` would otherwise be created as `Featured\?`).
  - "Row access only" is exact inside a New schema. In schemas that already existed when the data role was provisioned, `buildCreateUserSQL` ran `ALTER DEFAULT PRIVILEGES IN SCHEMA … GRANT ALL ON TABLES TO <data role>` as `postgres`, so tables `postgres` creates there give the data role ALL.
  - `SupabaseApiError.code` carries the SQLSTATE parsed from the error text (`ERROR:  42P07: …`), so `isDuplicateTableError` / `isInsufficientPrivilegeError` work on this path as on a `pg` error. A 429 (the Management API allows 120 requests a minute per project for our OAuth app) is retried with backoff in `executeQuery`.
  - **Fallback:** on `42501`, or the Management API answering 403, the old data-role DDL runs instead and `WSLogger.warn` logs it ("… refused; running it as the connection's own data role …"). That is expected for exports created before this change: their schemas and tables are owned by the data role, and `postgres` is not a superuser on Supabase. `createFields` falls back per field. Any other error (`42P07`, a bad statement, 401, 5xx, a timeout, an exhausted 429) propagates. The fallback cannot succeed inside a `postgres`-owned schema or on a `postgres`-owned table (the data role may not create or alter there); reaching it that way needs a 403 mid-export or a foreign key onto a legacy data-role-owned table, and surfaces the generic "Insufficient permissions…" message.
  - Side effect: adding a field to a customer's own `postgres`-owned table now works; the data role used to fail with "must be owner".
  - **Data API exposure (accepted, not mitigated in code).** On Supabase projects created before 2026-05-30, `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public` grants every new `public` table to `anon` / `authenticated` / `service_role` until Supabase enforces its new default on 2026-10-30, and tables created before then keep those grants ([changelog](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)). So an OAuth export into `public` — not the default New schema, which is a dedicated schema with no such defaults — creates tables the project's anon key can read and write through the Data API unless RLS is enabled. Tables our data role owned never got those grants. We chose to ship without enabling RLS or revoking; a customer exporting into `public` should `alter table … enable row level security` (our data role has BYPASSRLS) or revoke the grants. A connection string that logs in as `postgres` has always behaved this way.
- **Name limits are 63 BYTES, not characters (DEV-10906, shared with Postgres).** Postgres silently truncates an identifier over 63 UTF-8 bytes, so `POSTGRES_SCHEMA_CREATION_CAPABILITIES` declares `nameLengthUnit: 'utf8Bytes'`: Live Export elides over-long generated table/field names to 63 bytes (its `…` alone is 3 bytes), and the create-schema validator rejects a user-edited name over 63 bytes (e.g. 22+ CJK characters) with `FIELD_NAME_TOO_LONG` / `TABLE_NAME_TOO_LONG` instead of letting Postgres create the column under a clipped name the plan can't resolve. Columns created before this fix under a clipped name are not re-adopted by name on a re-plan. Generated **constraint** names must fit too: the auto primary key is declared on the `id` column so Postgres names it (knex's explicit `"<table>_pkey"` truncated to the table's own name for a 63-byte table name → 42P07 "already exists" on a table that didn't exist), and a foreign key whose knex default `<table>_<column>_foreign` exceeds 63 bytes gets a hashed ASCII name (`foreignKeyConstraintNameWithinPostgresIdentifierLimit`) so two FKs can't truncate into one (42710).
