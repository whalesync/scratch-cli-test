## Bulk operation limits / pagination
Max records (or fields) per API request, per operation. Zoho applies these **uniformly across all record modules** — no per-entity variation (so nothing extra in the entity-table notes). Source: `zoho-api-client.ts` constants, confirmed against the v8 API.

| Operation | Max per request | Mechanism | Notes |
|---|---|---|---|
| Read (list) | **200** records/page | `page_token` cursor (`GET /{module}`) | also capped at **50 fields/request** → connector splits wide modules across requests and merges by id. `page_token` tops out at **100,000** records; beyond that a module needs **Bulk Read** (not built — fails loud as `MODULE_TOO_LARGE`). |
| Create | **100** records/request | `POST /{module}` `{data:[…]}` | per-record results returned in a parallel `data[]`; partial failures surfaced, not swallowed |
| Update | **100** records/request | `PUT /{module}` `{data:[…]}` | each record must carry `id` |
| Delete | **100** ids/request | `DELETE /{module}?ids=a,b,…` | ignores not-found ids |

Separate org-wide **daily API-credit + concurrency** quotas apply (edition-based) on top of these per-request caps, and a **token-generation** rate limit on the OAuth token endpoint (see Gotchas) — both independent of bulk size.

## Incremental polling
- **Supported: YES.** Driver field = `Modified_Time` (annotated `x-scratch-last-modified-field`). `incrementalPullSupport` returns SUPPORTED whenever the module's schema carries it — nearly every record module does.
- **Mechanism:** an incremental pull sends `If-Modified-Since: <ISO 8601>` on the records list, so Zoho returns only records changed since. The **new watermark is the server `Date` response header, captured *before* the first page request** — so anything modified mid-run is simply re-pulled next time (idempotent, no gap). `If-Modified-Since` with nothing changed returns `204 No Content` → empty page, no watermark regression.
- **Deletions:** tombstoned via `GET /{module}/deleted?type=all` + `If-Modified-Since` (`listDeletedRecordIds`), so deletes propagate on incremental runs — not just creates/updates.

## Edge cases discovered
- **Emoji / astral chars → `?` (SERVICE-side, not the connector).** Zoho stores text fields as 3-byte `utf8` (not `utf8mb4`): BMP unicode (`テスト`, `ünïcödé`) round-trips intact, but 4-byte/astral characters like `🎯` are replaced with `?` by Zoho on write. Confirmed both through the connector **and** a raw-`fetch` probe (same result), so it's the service. The connector still stores verbatim what Zoho returns — no action needed beyond awareness.
- **`multi_module_lookup` naming gap (code).** Zoho's real `data_type` is `multi_module_lookup` (underscored), but `zoho-json-schema.ts` switches on `multimodulelookup` (no underscores). The underscored value falls through to the `default` branch — still stored verbatim/null (safe) but logs an "Unrecognized data_type" warning on every Notes schema build, and the explicit case is dead. Low-severity; storing verbatim is the intended outcome either way.
- **Niche reminder/recurrence data_types vary by org/module — `ALARM`, `RRULE`, `multireminder`.** Tasks/Events reminder + recurrence fields use opaque metadata types that differ across editions (the US org's Events used `ALARM`/`RRULE`; the EU org's used `multireminder` on `Remind_At`/`Remind_Participants`). All fell through to the `default` verbatim branch (+ a per-field warn on every schema build). **Fixed this run:** added `multi_module_lookup`/`ALARM`/`RRULE`/`multireminder` cases so they're typed verbatim (Unknown|Null) without the warning. Storing verbatim was always the intended behavior — this just silences the noise and documents intent.
- **Datetime tz fidelity (confirmed good).** Wrote `Events.Start_DateTime` as a UTC instant (`…+00:00`); Zoho stored/returned it in the org offset, but the **instant is identical** (no silent day/tz shift). The connector keeps it verbatim — round-trips cleanly.
- **Picklist = label, not id.** Single-select values round-trip as the literal display string (`"Cold Call"`, `"Lost Lead"`), so there is no id↔label translation to do — unlike many CRMs.
- **Datetime carries an explicit offset.** Values come back as `2026-06-04T13:41:19-07:00` (org TZ US/Pacific). Stored verbatim; tz-sensitive round-trip (write a `Z` time, read back in org offset) is the case to confirm in Pass 2.
- **Free-edition custom-field cap = 0.** Creating any of multiselectpicklist / percent / autonumber on this org returns `LIMIT_EXCEEDED` even with 0 existing custom fields — the edition allows none. A higher-edition org is required to seed-and-round-trip these specific custom types.

## Gotchas
- **Access-token generation limit (transient INVALID_TOKEN / pull "folders failed to load").** Zoho caps how many access tokens a single refresh token can mint in a short window; exceed it and freshly-minted tokens come back `INVALID_TOKEN` (401) and server pulls fail with "All folders failed to load". Hit during this run by minting many tokens across **separate processes** (each standalone debug script mints its own — the connector only caches within one instance). Mitigation: lean on the connector's cached token, avoid parallel one-off token mints, and wait ~10 min for the window to reset. Not a connector defect.
- **🚧→✅ Storage-cap gate (was blocking ALL creates; RESOLVED).** The legacy org ② sits at **25,164+ records** (Accounts alone = 25,094) against the free-edition **5,000-record cap**, so every `POST` returned `MAX_LIMIT_REACHED` ("maximum data storage limit") **org-wide**, not per module. Update/Edit and Pull were unaffected. **Resolved 2026-06-08 by provisioning the green-field EU org ①** (0 records → headroom) and running the create suite with `ZOHO_ALLOW_CREATE=1` → full CRUD now green. (Lesson for the playbook: on a capped org, prove writes via `updateRecords`; for create/delete, spin up a fresh free org.)
- **Edition gate (blocker for some custom-field types).** The test org can't add custom fields of several types — coverage of `multiselectpicklist`/`percent`/`autonumber`/`formula` needs a paid-edition org. Real, service-enforced; not a skipped step.
- **50-fields-per-request cap.** The records list caps at 50 fields/request; the client splits a wide module across requests and merges by id (`zoho-api-client.ts`).
- **Subforms & multiselectlookup only on single-record fetch.** Excluded from the list pull (`NON_LIST_DATA_TYPES`); a wide/inventory module would need the per-record hydrate path (v2).
- **page_token ceiling 100k.** Beyond it the connector fails loud (`MODULE_TOO_LARGE`) — Bulk Read is the v2 follow-up.
- **Server stack required for the full scratchmd publish ladder.** Connection/clone/pull/accept/upload/publish need the Scratch server (3010) + git service (3100/3101) running; not exercised this run.
