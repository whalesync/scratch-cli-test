**Org-wide rate/quota limits.** **10,000 requests/minute per app** and **25,000/minute per workspace** — the workspace ceiling is shared by every app installed on it, so a busy workspace can throttle us even when we are inside our own budget. Intercom enforces the per-minute figure in **10-second buckets of one sixth** the allowance, so a per-second `rateLimiterSpec` is the right shape (150/s = 9,000/min). Every response carries `X-RateLimit-Limit` / `-Remaining` / `-Reset`; **`X-RateLimit-Reset` is an absolute Unix timestamp in seconds**, so the wait is `reset - now` (contrast Brevo, whose reset header is a relative duration). `Retry-After` is undocumented — read opportunistically, never relied on. Job endpoints have their own concurrency caps that also surface as 429 (Data Export: 1 pending job/workspace). https://developers.intercom.com/docs/references/rest-api/errors/rate-limiting

**Transient server errors.** `502`/`503`/`504` are retried on the same exponential ladder as throttling (`isTransientIntercomServerError`, folded into `INTERCOM_RETRY_OPTS`); `X-RateLimit-Reset` is not used to pace them (it describes the rate-limit bucket), though a `Retry-After` is honored. On a **write**, a `500` is deliberately **not** retried — an article/collection create may have persisted before the error, so a retry could duplicate it. **Reads** (list, search, get, `/me`) use `INTERCOM_READ_RETRY_OPTS`, which also retries a `500` and network errors with no response (connection reset, timeout, DNS; `isRetryableIntercomReadFailure`), since repeating a read changes nothing. Before this, a single gateway `502` mid-walk failed a multi-hour conversations pull outright.

**A conversation Intercom lists but cannot return in full (`403`, or a 5xx that outlasts the retries, on `GET /conversations/{id}`).** Seen in prod (2026-10-19): one `403 Forbidden` on a single conversation's hydration, ~8 h into a ~156k-conversation Live Export pull whose token was hydrating every other conversation — so not a broken token. Likely cause: Intercom documents that an app token only reaches the conversations its authorizing teammate's "Conversation access" allows (https://www.intercom.com/help/en/articles/4707721-limit-teammates-access-to-conversations). The hydration loop no longer fails the folder on it: the conversation is kept **as the list endpoint returned it** (verbatim, just without `conversation_parts`) and reported as a pull record warning naming the conversation and Intercom's own `error.list` message, so the pull — and a Live Export run — **completes with a warning** instead of failing. The run's sync then **leaves that conversation out** (no create, no update), so its destination record keeps its existing message history instead of having it cleared by the partial copy. It is not dropped from the pull: a dropped conversation would read as deleted and the sync's delete policy would remove its destination record. The pull also clears the folder's incremental watermark, so the next pull is full and re-checks the conversation. More than 100 such conversations in one pull fails the folder (likely an access change, not a few restricted conversations). A conversation whose hydration keeps failing with a 5xx after every retry is handled the same way (its warning names the status; in an Intercom outage the next page's list call fails too, which still fails the folder). A `404` on hydration still drops the conversation (deleted between list and hydration); a throttle-coded error is retried as throttling; a `401`, throttling that outlasts the retries, or a network error that outlasts them still fails the folder. `pullRecordFilesByIds` (targeted re-pull) still throws on these.

**A conversations list or search page Intercom answers with `404`.** Seen in prod (2026-10-20): a ~156k-conversation Live Export pull failed ~6.7 h in, at page 2,327, on `404 Not Found` for the next page's `GET /conversations?starting_after=<cursor>`. The page before it kept at most 9 of its 20 listed conversations; the scratch-git proxy's response size gave the count, and every other page in the run kept 10–20. So conversations were being deleted right where the walk was. What we know (probed live, read-only, on the Whalesync workspace):
- **The cursor is a pure value bookmark**, `base64([updated_at_ms, id, page])`, and Intercom never looks its conversation up. A cursor naming a conversation that doesn't exist lists the right next page (200). Changing its `updated_at` shifts the results, and its page number only sets `pages.page`. An earlier cursor re-listed at any page size continues with no gap. So a deleted conversation can't break a cursor, and a saved cursor never goes stale.
- **The prod 404 didn't come from Intercom's normal API handling.** A malformed cursor answers `400 client_error`. A missing conversation and an unknown path both answer 404 with an `error.list` body. The prod 404's body had no `errors`/`message`/`error_code`. Likely causes: a passing error from Intercom's edge, or a page holding conversations just deleted but still in Intercom's list index. Both clear with time.

What the walk does (`paginateConversations`; timing in `IntercomConversationsWalkOptions`):
- **Retry:** list the page again from the same cursor 7 times, 2/4/8/16/32/64/120 s apart (about 4 minutes), in its own loop outside the rate limiter so a 404 doesn't freeze the connection's shared bucket. The cursor never goes stale, so a later listing picks up exactly where the walk stopped.
- **When the 404 outlasts that:** if the page before it was Intercom's last by Intercom's own count (`pages.page >= pages.total_pages`), the walk ends normally. Intercom hands out a cursor on its last page too, and the listing after it normally comes back empty. Anywhere else the folder fails with a user-facing `IntercomError`: "Intercom stopped returning conversations partway through the list: it kept answering "404 Not Found" for the next page after page X of Y for about 4 minute(s)…".
- **Why it doesn't just stop at the 404:** ending a walk early would read every unreached conversation as deleted, and VITL's sync deletes destination rows with no source match (`unmatchedDestinationPolicy.withMatchKey: delete`). The count can run slightly ahead of the walk (conversations deleted behind it lower `total_pages`), so trusting it can miss at most about as many conversations as were deleted behind the walk.
- **Not handled:** if a deleted conversation stays in Intercom's list index for more than ~4 minutes, no listing can get past it and the pull still fails. Testing that needs deletes, so it needs a throwaway workspace.
- **Tried and dropped (2026-10-20):** stepping back to earlier cursors with a smaller page. It assumed a deleted conversation kills its cursor, which the probes disproved.

**Failed-request logging.** `extractConnectorErrorDetails` puts the following into `additionalContext` for every Intercom HTTP error, including 401/403/timeouts and an `IntercomError` with an HTTP `cause`: the method, the full URL with its query (the access token is a request header and is never included), the status, Intercom's request id (`x-request-id` header, else `request_id` in an `error.list` body), the response headers (cookies left out, token-like headers masked), and the first 2,000 characters of the response body. The pull job logs it with "Phase 1 fetch failed for folder". Each list-page 404, the last one included, gets the same fields plus how long the failed listing took. A response from Intercom's app carries `x-runtime`, `x-ratelimit-*` and `x-intercom-version`, so a 404 without them came from Intercom's edge; an instant 404 points the same way. A retry that recovers logs an info line with how many retries and how long it took.

## Gotchas
- **Contacts:** `GET /contacts` is sorted by `last_seen_at` DESC (verified live) — never use it for a full walk; use the creation-order search walk.
- **Contacts:** a 401/403 on contacts/attributes means the token's Intercom app lacks **"Read and list users and companies"** — `testConnection` (`GET /me`) passes without it, so the connector rethrows naming the permission.
- **Contacts:** custom attribute keys are sparse (absent, not null, when never set) and names may contain spaces/capitals; date attributes are Unix seconds.
- **Contacts:** nested `tags`/`notes`/`companies` lists are stubs, at most 10 inlined (`has_more`/`url` for the rest); a contact's tag stubs carry no names.
- **Companies:** only companies with at least one contact are listable — a company that loses its last contact drops out of the scroll (within ~1–3 min, flapping meanwhile) and the next full pull removes it. Newly linked companies take 2–4 min to appear.
- **Companies:** the scroll lock is per WORKSPACE, so another integration scrolling the same customer's companies makes our pull wait (~90 s max) and then fail with an explanatory error; walks always run to the empty page so ours never holds the lock.
- **Companies:** `plan` is `{}` (not null) when unset; `remote_created_at`/`size`/`website`/`industry` are absent until set; custom string values over a few hundred chars are rejected by Intercom on write (`422 length too long`).
