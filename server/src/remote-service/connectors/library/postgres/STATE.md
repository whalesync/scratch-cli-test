## Gotchas
- **Field-value canonicalizers — representation churn (DEV-10556).** A SQL store returns what it was given for most columns, but re-renders three families on read-back: timestamps (`timestamptz`/`timestamp`/`date` → the driver's `…27.000Z` vs a source's `…27Z`/`…27+00:00`), floats (`0.30000000000000004` vs `0.3`) and `json`/`jsonb` (key order / whitespace). The shared `pg-common/pg-field-value-canonicalizer.ts` (registered as `resolveFieldValueCanonicalizer` since DEV-11420; the sync consults it for every user now that the rollout flag has been removed) compares `TIMESTAMP` columns as instants at millisecond precision, `NUMERIC` at 15 significant digits, `NUMERIC_STRING` (numeric/decimal/bigint strings, DEV-10777) as normalised decimal text — never through a float, so bigints differing beyond float64 precision stay different — and `JSONB` as parsed values; text/boolean/array columns compare structurally. A timestamp written into a `date` column genuinely loses the time of day and still diffs (DEV-11086 is the schema fix; not papered over). A `date` column also only converges on a **UTC server**: the pull parses the date OID into a JS Date at local midnight, so a non-UTC server stores `2026-05-01T07:00:00.000Z` for a source `2026-05-01` and the instant compare rightly diffs — a pull bug (F1 in `LIVE_EXPORT_AUDIT.md`, pass-through date parser), invisible in production where servers run in UTC. See `pg-common/__tests__/pg-field-value-canonicalizer.spec.ts` and [CONNECTOR_GUIDE → Field Value Canonicalizers](../../CONNECTOR_GUIDE.md#field-value-canonicalizers-diff-stability).
- (connector-specific operational notes)
- **Visible since 2026-10-27, and a launched Live Export destination.** `visible: true` shows Postgres in the Scratch web and desktop connector pickers. Separately, Whalesync's `LIVE_EXPORT_DEST_SERVICES` flag serves `POSTGRES` in production's `LAUNCHED` list (and bottlenose's `LIVE_EXPORT_DEST_SERVICES_DEFAULT` fallback). Destination audits: `airtable/LIVE_EXPORT_AUDIT.md` (Airtable → Postgres) and `mysql/LIVE_EXPORT_AUDIT.md` (MySQL → Postgres), both against a local Postgres. The connection-security checks below are what made it safe to offer.
- **Connection security (DEV-12390, shared with Supabase).** Two checks sit between a user's connection string and node-postgres. (1) The allowlist in `pg-common/node-postgres-connection-string.ts`, run by `PostgresAuthParser` on create and edit and again by `KnexPGClient` on every connect: node-postgres's `pg-connection-string` copies every query parameter into the client config, and `sslrootcert` / `sslcert` / `sslkey` make it `fs.readFileSync` a path on our server before connecting (`/dev/zero` would block the process until it ran out of memory). Those, the URL overrides (`host`, `hostaddr`, `port`, `user`, `password`, `dbname`, `database`), `replication`, Unix-socket hosts, other `sslmode` values and `options` other than a Neon endpoint ID are refused with a message that never echoes a value; only `sslmode`, `ssl=true`, `uselibpqcompat`, `application_name` and Neon's `options` reach the driver, and everything else (`pgbouncer`, `schema`, `connection_limit`, `channel_binding`, timeouts, `binary`, `client_encoding`, ...) is dropped. The stored string stays as typed. (2) The database host guard: in deployed environments node-postgres opens every socket through `SsrfSafeSocket` (`connectors/utils/ssrf-safe-socket.ts`, ported from Whalesync), which refuses loopback / private / link-local / metadata addresses after its own DNS lookup and connects only to the addresses it vetted (no rebinding, `?host=` overrides covered, TLS SNI unchanged). A refusal and an unresolvable host both show `POSTGRES_HOST_NOT_REACHABLE_MESSAGE`, which names the egress IP to allowlist; the refused address is logged only. A customer database must have a public address. Covered by `pg-common/__tests__/node-postgres-connection-string.spec.ts` and `server/test/integration/postgres-database-host-guard.spec.ts`; checked by hand through the guard against a public Postgres (plaintext and TLS) on 2026-10-27.
- **Exact native column types in Live Export (DEV-11903, shared with Supabase).** The read side annotates every column with `x-scratch-native-column-type: { typeSystem: 'postgres', type, isRecreatableVerbatim }`, where `type` is the exact `format_type(atttypid, atttypmod)` spelling (`integer`, `text[]`, `numeric(12,2)`, `character varying(50)`), read from the catalog join in `KnexPGClient.findAllColumnsInTable`. When a Live Export targets a Postgres-type-system destination (Postgres or Supabase — `POSTGRES_SCHEMA_CREATION_CAPABILITIES.nativeTypeSystem`), the plan carries each recreatable type as `CreateFieldSpec.nativeFieldType`, keeps the source column names verbatim, and `pg-create-schema.ts` creates the column with that exact type. Recreatable = a built-in (`pg_catalog`) type in the allowlist of `pg-common/pg-native-column-type.ts` whose pulled value writes back unchanged; `bytea` (pulled as Node's `{type:'Buffer',data}`), `interval`, enums/domains/extension types and `json[]`/`jsonb[]` fall back to the logical mapping. The same predicate gates `specificType` on create, so a client-supplied native type can never inject DDL. Cross-service sources get the richer logical types instead: an array of primitives becomes a list column (`text[]`/`integer[]`/`boolean[]`, `fieldType.isArray`) and an object a `jsonb` (`json` kind). Any other array (e.g. of objects) still flattens to text: a `jsonb` column declares no shape, so the sync's transform picker would join an array into one string before writing it. Inserts send an ARRAY bound for a `json`/`jsonb` column as its JSON text (`pg-json-column-insert-serialization.ts`, applied via the shared `prepareRecordsForPgInsert`) — the driver otherwise binds a JS array as a pg array literal, which is invalid JSON; strings and objects insert exactly as before. Covered end-to-end against a real database in `server/test/integration/postgres-native-column-types.spec.ts`.
- **A `?` in an identifier inlined into `knex.raw` is a binding placeholder (shared with Supabase).** The bulk `updateMany` / `deleteMany` statements are hand-written raw SQL, so every schema, table and column name in them goes through `quotePostgresIdentifierForKnexRawSql`, which escapes `?` as `\?`. Without that, a column such as `Decisionmaker?` failed every edit with "Expected 1 bindings, saw 3" (2026-10-16, HubSpot → Supabase Live Export). The query-builder paths get the same escape from `escapeKnexColumnIdentifierSpecialCharacters`. Any new raw statement that inlines identifiers must use the helper. Knex query-compilation errors map to "The SQL query for this change could not be compiled: <statement>" (`pg-knex-query-compilation-error.ts`) rather than `PostgreSQL error: <knex internals>`. The bulk raw statements run through `runKnexRawStatementTaggingCompilationErrorWithSqlText` so the statement template is known. On the query-builder and DDL paths, the `wrapIdentifier` hook (`knex-column-identifier-dot-encoding.ts`) quotes identifiers itself, because knex reads `[<digits>]` as an array subscript. Edge whitespace in a column name is sentinel-encoded, because knex trims identifiers. A column named exactly `*`, or one with a backslash immediately before a `?`, is still unsupported.
- The FK annotation carries two forms of the target: `linkedTableId`, a display string that drops a `public.` prefix (`authors`, `taxonomy.categories`), and `linkedTableRemoteId`, the linked table's full remote id `[schema, table]` — which keeps `public` so it deep-equals that table's `DataFolder.tableId` and can be matched by array equality.
- **Name limits are 63 BYTES, not characters (DEV-10906, shared with Supabase).** Postgres silently truncates an identifier over 63 UTF-8 bytes, so `POSTGRES_SCHEMA_CREATION_CAPABILITIES` declares `nameLengthUnit: 'utf8Bytes'`: Live Export elides over-long generated table/field names to 63 bytes (its `…` alone is 3 bytes), and the create-schema validator rejects a user-edited name over 63 bytes (e.g. 22+ CJK characters) with `FIELD_NAME_TOO_LONG` / `TABLE_NAME_TOO_LONG` instead of letting Postgres create the column under a clipped name the plan can't resolve. Columns created before this fix under a clipped name are not re-adopted by name on a re-plan. Generated **constraint** names must fit too: the auto primary key is declared on the `id` column so Postgres names it (knex's explicit `"<table>_pkey"` truncated to the table's own name for a 63-byte table name → 42P07 "already exists" on a table that didn't exist), and a foreign key whose knex default `<table>_<column>_foreign` exceeds 63 bytes gets a hashed ASCII name (`foreignKeyConstraintNameWithinPostgresIdentifierLimit`) so two FKs can't truncate into one (42710).
