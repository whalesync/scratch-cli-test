## Edge cases discovered
- **Symmetric (`dual_property`) relations — reciprocal FK dedup (DEV-10753).** A Notion `dual_property` relation is two-way: the linked database carries a mirror relation. The generated `relation` schema now surfaces `inverseFieldId` (from `relation.dual_property.synced_property_id`) on its `x-scratch-foreign-key` annotation, so the create-plan generator recognizes the reciprocal pair and suggests only ONE side when both databases are in a Live Export plan. A `single_property` relation is one-way and carries no `inverseFieldId`. Notion relations are always multi-valued (N→N), so `isSingleValued` is never set; `NOTION_SCHEMA_CREATION_CAPABILITIES` declares `supportsManyToManyForeignKeys: true`. See `notion-json-schema.ts` `case 'relation'` and the regression test in `notion-json-schema.spec.ts`. **The live `fetchJsonTableSpec` snapshot may move** if the test database has a dual_property relation — regenerate with `yarn run test:integration notion-connector -u`.
- **Multi-value source → text field comma-joins EVERY value; the old "first value only" warning was wrong and is gone (DEV-10956 → DEV-11076).** A multi-valued source (Postgres `text[]`, an Airtable multi-select) Live-Exported into a created Notion text field lands with **all** elements joined (`int[]` `[1,2,3]` → `"1, 2, 3"`), not take-firsted. It briefly did take-first — a Notion `rich_text`/`title` property is an `object` envelope, which fails the picker's `TEXT_LIKE_DESTINATION_LOGICAL_TYPES` check — and `NOTION_SCHEMA_CREATION_CAPABILITIES` declared `keepsOnlyFirstValueWhenMultiValueMappedToTextField: true` so the create plan would warn about the loss. DEV-10952 then gave the inbound packs `fromCoreInputType: 'string'`, and `transform-picker.ts` collapses on the declared pack input type ahead of the envelope's raw logical type — so every such mapping joins and the warning became false for every case it could fire on (`text`/`longText` create fields are always `title`/`rich_text`, both string packs). The capability and its note were removed; an array source now gets the same accurate `downgraded` note here as on every other destination ("Can't unpack this array field, syncing as plain text"). See `schema-builder-plan-generator.ts` (`inferLogicalFieldType`) and `transform-picker.ts`.
- **Database names are not unique — no create-time dedup against existing databases (DEV-10943).** A Notion page may contain any number of databases sharing a title, so `NOTION_SCHEMA_CREATION_CAPABILITIES` declares `requiresUniqueTableNames: false`. The create-plan generator (Live Export "tables & fields" editor) therefore does NOT rename a brand-new database against existing ones; it previously scanned the whole workspace (`listTables`, which is unscoped for Notion — a database's `remoteId` is `[databaseId, dataSourceId]`, never the parent page) and appended spurious ` 2`/` 3` suffixes to freshly-created databases. In-plan duplicate names within a single create request are still deduped, since the request rejects same-named tables (`DUPLICATE_TABLE_NAME`). See `schema-builder.service.ts` `generatePlan` and `notion-create-schema.ts`.
- **Date properties emit date-only AND full date-time.** Notion serializes an all-day date as `"2025-02-20"` (no time component) and a timed date as full RFC3339 (`"2025-02-20T13:00:00.000-05:00"`). The generated `date` property schema models `start`/`end` as a `format:'date'` | `format:'date-time'` string union so both validate. A single `format:'date-time'` was rejecting every all-day date in the CLI's `enforce_schema` validator (which runs with `should_validate_formats(true)`) — the highest-volume false error on a fresh pull. See `notion-json-schema.ts` `case 'date'`.
- **Page icons have non-emoji/file shapes.** Besides `emoji`/`external`/`file`/`null`, Notion returns a built-in named icon `{type:'icon', icon:{name, color}}` and a `{type:'custom_emoji', custom_emoji:{id, name, url}}`. The top-level `icon` union models all of them. The named-`icon` branch carries no URL (not a rehostable asset, so `extractUrl` skips it); `custom_emoji.url` is extracted like file/external icons. See `notion-json-schema.ts` `icon`.
- **`people` properties can contain groups, not just users.** A workspace/teamspace group mentioned in a Notion person property is returned verbatim as `{ id, object:'group', name }` (no `person` sub-object), alongside the usual `{ object:'user', … }` members. The generated `people` item schema therefore models `object` as `Type.Union([Type.Literal('user'), Type.Literal('group')])` so group members validate; a single `const:'user'` made the CLI's `enforce_schema` reject every group member with `"user" was expected` (19 false-positive errors on the Optemization design-partner workspace — DEV-10571). The `created_by`/`last_edited_by` system fields (and the `notionUserObjectSchema` behind them) keep `const:'user'` — a page's actor is always a user, never a group. See `notion-json-schema.ts` `case 'people'` and the regression test in `notion-json-schema.spec.ts`.

## Gotchas
- **Create-destination deep link is built from the id, not the API's `url`.** `buildCreateDestinationRemoteWebUrl` returns `buildNotionPageWebUrl(pageId)` = `https://www.notion.so/{id-without-dashes}`. `PageObjectResponse.url` is also on hand (and carries a title slug), but the hook is contractually pure/sync/network-free so it can be called across a whole picker list — and the bare-id form resolves to the same page. Shared with the per-table `remoteWebUrl`.
- **url/email property values are free-text — no `format` assertion (fixed).** Notion does not validate the content of `url`/`email` properties; the API returns verbatim whatever the user typed — schemeless domains (`"lu.ma/adithya"`), phone numbers, Twitter handles (`"@_adenab"`), notes (`"Yohei tweet"`), even multiple comma-separated emails. The `url`/`email` property types are therefore modeled as plain nullable strings (`Type.Union([Type.String(), Type.Null()])`, like `phone_number`), with **no** `format:'uri'`/`'email'` — otherwise the CLI's `enforce_schema` validator (`should_validate_formats(true)`) rejects that legitimate data. (Previously these carried `format` and surfaced 109 false-positive errors in the Whalesync Internal workspace.) url **column** display-typing is preserved by keying the `'url'` column type off `x-scratch-connector-data-type === 'url'` in `notion-default-view.ts` (`resolveNotionPropertyColumnType`) rather than off the dropped format. See `notion-json-schema.ts` `case 'url'`/`'email'` and the regression tests in `notion-json-schema.spec.ts` + `notion-default-view.spec.ts`. The fixed page `url` system field keeps `format:'uri'` (always a real URL).
