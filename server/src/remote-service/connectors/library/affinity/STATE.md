## Incremental polling

- **Supported:** **NO — not feasible for the main entities; confirmed with live API evidence 2026-06-11.** Only cursor _resume_ checkpointing exists (`pullRecordFiles` threads `progress.cursor`); there is no last-modified driver field, no `x-scratch-last-modified-field`, and no `incrementalPullSupport`. Each pull is a full fetch — **and the API gives us no way to change that for the entities that matter.**
- **Live evidence (whalesync org):** a future-dated modified-since filter must return 0 rows if honored; it returned the **full set** for every main entity → the filter is **silently ignored** (HTTP 200, no narrowing):
  | Entity | API | modified-since filter | no-filter count | future-date count | verdict |
  |---|---|---|--:|--:|---|
  | Persons | v2 | `filter=updatedAt>=…` | 18 | **18** | ignored |
  | Companies | v2 | `filter=updatedAt>=…` | 39 | **39** | ignored |
  | List entries | v2 | `filter=updatedAt>=…` | 5 | **5** | ignored; **records carry no row-level modified ts at all** (only `createdAt`) |
  | Persons | v1 | `?min_last_modified=…` | 18 | **18** | ignored |
  | **Notes** | v2 | `filter=updatedAt>=…` | 10 | **0** | **HONORED** (also narrows: `>=2020`→2) |
- **The one exception (Notes) is still unsafe to wire:** `updatedAt` is **`null` on never-edited notes** (8 of our 10, incl. notes created Apr 2026). An `updatedAt>=watermark` incremental would **silently drop every note created-but-never-edited after the watermark** — data loss. A correct Notes-incremental needs `createdAt>=W OR updatedAt>=W`, which the single-field `x-scratch-last-modified-field` hook can't express. Wiring incremental for one small table (Notes) at this risk, while every large table stays full-pull, isn't worth it.
- **Mechanism:** n/a — no `since`/modified-since filter wired (and none works for persons/companies/list-entries/opportunities).
- **Deletions:** not detected (no incremental).
- **Verdict:** **DEV-10159 ("Affinity incremental polling") was correctly canceled** — now backed by evidence, not assumption. Revisit only if Affinity adds a row-level modified timestamp + honored filter to the v2 list endpoints.

## Publishing / write support (DEV-10298)

**Status (2026-06-11): Phase 1 IMPLEMENTED, not yet live-verified.** `updateRecords` pushes changed field values through the v2 `update-fields` batch endpoints (read-shape → write-shape narrowing in `affinity-write-translation.ts`: dropdowns → `{dropdownOptionId}`, person/company refs → `{id}`, locations → 5 write keys; truncated multi-value reads are refused to avoid deleting unfetched values). Research (Affinity **v2** docs + Whalesync's direct **v1** connector at `../whalesync/api/bottlenose/src/connectors/affinity-connector/`) shows publishing is **partly v2-native, partly v1-only**:

**Supported on v2 now (same Bearer token, several BETA) — do these first:**

- **Edit a field value** (the common edit→push): `POST /v2/{persons|companies}/{id}/fields/{fieldId}` (single) · `PATCH /v2/{persons|companies}/{id}/fields` (batch, ≤100 fields) · list entries `…/list-entries/{id}/fields[/{fieldId}]`. Body is a **typed value object** `{ "value": { "type": "<field-type>", "data": … } }`, ids for refs/dropdowns (e.g. `{"type":"company-multi","data":[{"id":1}]}`) — matches the read-side reindex-by-field-id model.
- **Notes**: `POST /v2/notes` (create) · update · `DELETE` — full CRUD. **Lists**: create a list; CRUD a list field's dropdown options. **Reminders**: create.

**NOT in v2 — needs v1** (Whalesync's proven path; v1 uses Basic auth with the key as password — or test whether the v2 Bearer token authorizes v1, as it already does for `/entity-files`):

- **Create / delete whole records** (persons, companies, opportunities) → v1 `POST`/`DELETE /persons|/organizations|/opportunities`. So **New→Push and Delete→Push of records are v1-only.**

- **List membership** (add/remove a record to a list): v1 `POST`/`DELETE /lists/{id}/list-entries`.

**Plan:** Phase 1 = v2-native field-value edits + Notes CRUD (covers the "edit existing records" ask for DEV-10298, no new auth). Phase 2 = add a v1 codepath for record create/delete, opportunities, and list membership only if customers need them.

## Foreign keys / associations

**The Entity-Files parent refs are declared FKs (2026-06-11).** They're the connector's only **clean** FK surface — bare scalar ids on a top-level column, exactly the shape `x-scratch-foreign-key` needs. Every other Affinity reference is a **decorated object** (`{id, name, …}`) nested inside a field value, which a plain FK annotation can't target (see the limitation below).

| FK field → target table                                           | Read (pull) | Write via CLI (move parent→parent) | Notes                                                                                                 |
| ----------------------------------------------------------------- | :---------: | :--------------------------------: | ----------------------------------------------------------------------------------------------------- |
| `entity-files.person_id` → `People` (`persons`)                   |     ✅      |                 ➖                 | declared; read-only (no v1 metadata-update endpoint), so move is N/A — link followed, not re-parented |
| `entity-files.organization_id` → `Companies` (`companies`)        |     ✅      |                 ➖                 | declared; read-only                                                                                   |
| `entity-files.opportunity_id` → `Opportunities` (`opportunities`) |     ✅      |                 ➖                 | declared; read-only                                                                                   |
| person / person-multi **field value** → `People`                  |     ❌      |                 ❌                 | **not declarable as-is** — value is `value.data` = `{id,…}` / `[{id,…}]`, not a scalar column (below) |
| company / company-multi **field value** → `Companies`             |     ❌      |                 ❌                 | same — decorated object nested in the field value                                                     |
| list entry `listId` → its List                                    |     ➖      |                 ➖                 | not an FK: `listId` is the _table identity_ (which list this entry is in), not a row in another table |

> Read ✅s (2026-06-11): pulled the Entity Files table, confirmed the schema carries `x-scratch-foreign-key: {linkedTableId}` on all three id fields, and that the one entity file's `person_id` (168116437) resolves to a real People record ("Example Person") in both the local table and the service API.
>
> **Limitation — the real CRM relationship fields (person/company references) are NOT declarable as FKs without reshaping.** Their value lives at `entity.fields.<id>.value.data` as a decorated object (single `{id, firstName, …}`) or array (`[{id,…}]`). `x-scratch-foreign-key` needs the field's _value_ to BE the bare foreign id (like Copper's `primary_contact_id: <number>`); here the id is buried inside a decorated object/array, and per the connector-build playbook arrays are leaves on the editable path. Making these real FKs requires reshaping `value.data` to surface the bare id as a keyed scalar column on pull (and reversing on publish) — a verbatim-fidelity + write-translation change. **Deferred as a flagged design decision** (see PLAN.md → "Foreign-key reshaping"), not done unilaterally: the relationships already round-trip correctly as values (writes verified), so this is a linking/UX enhancement, not a correctness fix.

## Edge cases discovered

All found during the 2026-06-11/12 live write passes:

**Pass-2 write boundary sweep (2026-06-12, direct API on a throwaway person):**

- **Emoji / unicode are preserved** (utf8mb4): `café ☕ 日本語 🎯 emoji` round-trips byte-exact through a text field value, and emoji survive in a person name too. Affinity does **not** strip astral chars (contrast Zoho, which replaces emoji with `?`). No connector handling needed.
- **Long strings accepted** — a 5000-char text value round-trips with no truncation. (Didn't probe the exact ceiling; nothing truncated at 5000.)
- **Numbers are float-typed server-side** — integer writes read back as floats (`0`→`0.0`, `-42`→`-42.0`, `999999999999`→`999999999999.0`); decimals and negatives preserved. Benign for round-trip (JS `JSON.stringify` drops the trailing `.0`), but worth knowing the stored shape is a float.
- **Multi-value writes cap at 100 items** per field (v2 `maxItems: 100` on the write payload) — a >100-value field can't be set in one call. Not hit in the test org; note for a future bulk case.
- **Empty/null clears** the service accepts fine (the CLI-side drop is the platform bug, [PLAN.md](./PLAN.md) P4).

- **Person names are title-cased on create (v1).** `POST /persons {first_name: "ZZZ-CLI-P2"}` reads back as `"Zzz-cli-p2"` — Affinity normalizes person-name casing on create. So a New→Push person doesn't round-trip byte-exact; the create patch lingers in `files unpublished` until discarded (same shape as the date-snap / hydration phantom-patch family, [PLAN.md](./PLAN.md) P6). An already-mixed-case edit (`ZZZCLIRenamed`) is left untouched. Company `name`/`domain` and opportunity `name` are NOT case-normalized.

- **Date fields are day-granularity and snap to org-tz midnight.** Writing `2026-06-15T10:30:00Z` to a (v1-created, `value_type: 4` Date) field read back as `2026-06-15T07:00:00Z` — midnight in the org's timezone (PDT). Time-of-day does not survive; the value will not round-trip byte-equal, so the local edit becomes a phantom pending patch after the next pull.
- **Reference values hydrate on read.** Writing `{id}` (person/company) or `{dropdownOptionId}` (dropdowns) succeeds, but the service reads back the hydrated object (`{id, firstName, …}` / `{dropdownOptionId, text, rank, color}`) plus a `totalCount` sibling on multi values. Consequence: a sparse user edit never byte-matches canonical, so the CLI's value-based re-anchor keeps the patch pending forever and logs a conflict (`conflicts.log`) even though the publish landed. Workaround: `files discard` after a confirmed publish, or edit using the full hydrated shape. (Cross-connector pattern — filed for a platform fix.)
- **Field clears are silently dropped by the CLI publish path** (platform bug, not Affinity): the CLI's patch dialect is JSON merge-patch (`null` = delete key) while the publish plan's `computeChangedFields` intentionally ignores deleted keys — so a cleared field produces an empty diff, the record is skipped, and the CLI prints "Published". Affinity itself accepts `{type, data: null}` clears fine (verified raw). Also bites _nested_ nulls: a location written with `"state": null` can never converge with the stored patch.
- **Multi-folder publishes only commit the first folder's batch to `main`** (platform bug): a single publish touching People + Companies wrote both to the service but only People got the `Publish V2 edit batch` commit; the Companies file stayed stale on main/dirty with everything reporting success. Re-publishing the leftover patch alone healed it.
- **Truncated multi-value reads would destroy data on write** — multi values carry `totalCount`; when `totalCount > data.length` the read is paginated-truncated, and writing it back would delete the unfetched values. The connector refuses these writes (`affinity-write-translation.ts`).
- **`GET /v2/notes/{id}` content differs by note type:** `interaction`-type notes have `content.html: null`. Note updates are rejected by Affinity when the note contains @mentions.
- **v1 field creation on a list must match the list's model type** — `entity_type` is the type of entity the list _holds_ (Deals holds companies → `entity_type: 1`), not "opportunity because it's a deal list"; mismatch → `422 "List EntityAttribute must have same model type as list type"`.
- **v1 and v2 API keys are interchangeable** (see Gotchas) — one credential covers a future v1 write path.

## Gotchas

- **Two API versions in one connector:** persons/companies/opportunities/notes/lists use **v2** (cursor pagination); Entity Files uses **v1** (`next_page_token`). Watch for shape/auth differences between them.
- **Opportunities are intentionally thin** (id/name/listId) — v2 has no `/opportunities/fields`; their custom values live per-list via list-entries.
- **Field values are an array reindexed to an object keyed by field `id`** before storage; values are addressed by remote field id (`x-scratch-remote-field-id`), not by name.
- **`/rate-limit` has no `/v2` prefix** (v1-era endpoint), unlike the rest of the v2 surface.
- **v1 and v2 API keys are fully interchangeable** (tested live 2026-06-11: v1 key and v2 key each return 200 on both `GET /persons` (v1) and `GET /v2/lists` (v2), as `Bearer` **or** HTTP Basic key-as-password). One stored `apiKey` credential covers any future v1 write path — no second credential needed for DEV-10298 phase 2.
