Inbound (Marketplace-Initiated) OAuth Routing

How a GoHighLevel “Install” click turns into a connected workbook in Scratch — even when the person arriving has no session, no workbook, and maybe no account yet. Connector-agnostic; the shape is borrowed from Whalesync’s Webflow flow. Companion to inbound-oauth-routing.md and inbound-oauth-plan.md.

01The flow at a glance

GoHighLevel marketplace Scratch web app · app.scratch.md Scratch API · api.scratch.md Database Clerk auth
1
Marketplace

User clicks Install → picks a Location → 302 to the web app

GHL’s chooselocation consent returns a one-time code and redirects the browser to the web host (not the API).

https://app.scratch.md/oauth/install/hl?code=<one-time>

Slug is hl, not a brand word — GHL rejects redirect URLs containing “ghl/highlevel”.

2
Web page (public)

Landing page reads the code and relays it

A public Next.js page reads ?code= and immediately POSTs it to the API. Strict-Mode-guarded so the single-use code is only redeemed once.

client/src/app/oauth/install/[service]/page.tsx
3
API (public)

Redeem the code now & stash encrypted tokens

The code expires in minutes, so it’s exchanged for tokens up front, encrypted (AES-256-GCM), and written to a single-use, 1-hour PendingOAuthInstall row. Returns { installId } as JSON (no 302).

POST /oauth/install/:slug → OAuthInstallService.redeemAndStashInstall
4
Database

PendingOAuthInstall — the orphan-token parking spot

id = pin_… (unguessable bearer secret) · encryptedCredentials · workspaceId (GHL locationId) · expiresAt = now + 1h. Independent table, no FKs — safe to deploy in any order.

5
Web → claim page

Forward to the auth-gated claim page

The page hands off only the installId — the GHL code is already spent.

router.replace('/connect/hl?install=<installId>')
6
Clerk middleware

Sign up / sign in if needed (states A · B · C)

The claim page is not public, so Clerk handles the three auth states for free; the installId survives the detour in the URL via returnBackUrl. See §02.

client/src/app/connect/[service]/page.tsx
7
API (auth)

Claim: reserve → create workbook → real connection

Atomic single-use reserve (flips claimedAt), auto-creates a workbook, moves the tokens into a real ConnectorAccount (OAUTH_SYSTEM), deletes the pending row. Rolls everything back on failure.

POST /oauth/pending-install/:installId/claim → claimInstall
8
Web

Land in the new workbook — HighLevel connected ✓

User is dropped into the freshly-created workbook with the connection live.

02The three auth states (resolved at step 6, no per-state code)

A · No account

Brand-new user

Clerk → sign-up → email verify → back to the claim page (case C). The 1-hour TTL bounds how long they have.

B · Logged out

Has an account, no session

Clerk → /sign-in?redirect_url=/connect/hl?install=… → back to the claim page (case C).

C · Logged in

Active session

Claim page renders, GET /oauth/pending-install/:id loads metadata (never tokens), user clicks Connect.

The installId is the only thing threaded through sign-up / sign-in. The fragile one-time GHL code was already consumed at step 3, so no login detour can break it.

03Borrowed from Whalesync’s Webflow flow

Whalesync (sister repo at ../../whalesync) solved the same marketplace-initiated problem for Webflow. Scratch borrows the skeleton and hardens the correlation.

Same shape ✓

  • Land on a public web page, not the API host.
  • Redeem the code immediately, server-side, on landing.
  • Stash tokens in a short-lived, encrypted “pending” record — both 1-hour TTL.
  • Convert to a real connection only after auth — both via Clerk.

What Scratch changed →

  • Correlate by an unguessable single-use installId, not the installer’s email.
  • Claim is an explicit “Connect” click, not an auto-sweep of the email’s pending rows.
  • The whole detour rides one URL carrying the token through Clerk.
  • Claim provisions a fresh workbook for the new ConnectorAccount.

04Why the installId is a bearer secret

High entropy · pin_ + 32 random bytes Single-use · deleted on claim Short TTL · 1 hour Auth required · claim needs a Scratch user Atomic reserve · no double-claim Encrypted at rest · AES-256-GCM
Inbound gets separate endpoints precisely so the app-initiated path keeps its state.userId === actor.userId check intact — inbound can’t weaken it.
