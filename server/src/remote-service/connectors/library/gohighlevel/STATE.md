### 1. Structural entities — define the record path in Scratch
**Record path:** `/{Standard Objects|Custom Objects}/{Entity}/{record}.json`. A Private Integration Token is scoped to **one Location** (sub-account), so the Location is the **connection scope, not a path segment**. Entities are grouped into a **type folder** for clarity: all built-in GHL entities (Contacts, Opportunities, Pipelines, Companies/`business`, Calendars, …) live under **`Standard Objects/`** (`basePath = ['Standard Objects']`); only **human-defined custom objects** (`custom_objects.*`, e.g. Pets/Posts) live under **`Custom Objects/`** (`basePath = ['Custom Objects']`). The split is by object key: `custom_objects.*` → Custom, everything else → Standard. Compare Airtable `/{base}/{table}/{record}.json`.

|---|---|---|
| Location (sub-account) | the connection scope; the PIT is scoped to one | — (the connection, not in path) |
| **Type folder** (`Standard Objects` / `Custom Objects`) | groups built-in entities vs human-defined custom objects | **path segment** (`basePath`) |
| **Entity** (Contacts/Opportunities/Custom Object/…) | the table — its records are files | **path segment** (the table itself) |

## Custom fields / Custom Objects (the dynamic part)
Distinction: a custom **field** is a **column on an entity** (Contacts/Opportunities) → field-types, not an entity. A custom **object** is a user-defined **record type** → it's a main entity (table 2 above).
- Contacts/Opportunities custom fields discovered from `GET /locations/{locationId}/customFields` (filtered by `model`). Stored verbatim as `{ id, <valueKey> }` — **valueKey is `value` for Contacts, `fieldValue` for Opportunities**; write shape `{id, field_value}` for both.
- **2026-06-09: the location had ZERO custom fields → SEEDED all 13 dataTypes via API** (`POST /locations/{id}/customFields {name,dataType,model}` → 201; CLI/no-browser). **Live dataType enum (corrected from the OpenAPI guess):** `TEXT, LARGE_TEXT, NUMERICAL, FLOAT, MONETORY, PHONE, TIME, DATE, CHECKBOX, SINGLE_OPTIONS, MULTIPLE_OPTIONS, RADIO, FILE_UPLOAD`.
  - ⚠️ **`EMAIL` is NOT a valid custom-field dataType** (422 — it's a standard contact field). The OpenAPI list was wrong.
  - ⚠️ **`FLOAT` and `TIME` exist** and weren't in the connector's documented set → **verify the json-schema maps them** (memory listed only TEXT/LARGE_TEXT/NUMERICAL/PHONE/MONETORY/SINGLE/MULTIPLE/DATE/CHECKBOX/FILE_UPLOAD — FLOAT/TIME/RADIO may be unmapped).

- **2026-06-09 — ALL 18 tables pull cleanly via the connector** (workspace `wkb_v8Sy6Oy7I9`/`coa_m4Gwt30pFK`): blog_authors, blog_categories, calendar_groups, calendars, campaigns, business(Companies), contacts, conversations, forms, opportunities, pipelines, custom_objects.posts(Posts), products, proposals, surveys, trigger_links, users, workflows. - **Per-entity pagination** is bespoke (searchAfter/startAfter/page/skip/offset/cursor). Contacts `searchAfter` is the unverified one (>100 contacts) and is **stripped from each record before storage** (transport, not data).
- **Opportunities** is the only endpoint using `location_id` snake_case; its customFields valueKey differs from Contacts.

- **`_id` vs `id` per entity.** Products / Proposals / Blog Authors / Blog Categories use **`_id`**; everything else uses `id`. The connector's `idField` config handles it — but it's the reason a record can look like it "only has `_id`".
- **2026-06-22 — Calendars `openHours` is object-OR-array (verbatim type mismatch → was failing validation).** HighLevel returns `openHours` as an **array** of open-hour blocks when the calendar has hours configured, but as an **empty object `{}`** when it doesn't. It was typed `array` in `GOHIGHLEVEL_ENTITY_FIELDS`, so a fresh pull of an unconfigured calendar failed `enforce_schema` (`{} is not valid under … 'anyOf'`). Fixed by typing it `unknown` (accepts either). **Gotcha within the gotcha:** the *persisted* problems index (`get-folder-problems`) reported this folder clean while `validation dry-run` on the same record flagged it — the index was stale, so **trust `validation dry-run` over the index when verifying a schema fix.**
- **2026-06-22 — Calendars create needs only `name`.** `POST /calendars/` with `{locationId, name}` succeeds (201); every other field defaults server-side. Update (`PUT /calendars/{id}`) merges per field, so a sparse one-field edit is a valid partial write. Both responses wrap the object in `{ calendar: … }`.
