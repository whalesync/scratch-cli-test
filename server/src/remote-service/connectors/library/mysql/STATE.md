## Incremental polling

- **Supported:** YES, per folder. Driver field = the user-declared `modifiedAtField` advanced setting (a `field-select` limited to formats `date-time` = TIMESTAMP and `date-time-local` = DATETIME). There is no `x-scratch-last-modified-field` annotation and **no auto-detect in v1**: an `ON UPDATE CURRENT_TIMESTAMP` column can still be NULL on new rows (no `DEFAULT`), and NULL rows are never pulled incrementally; a DATETIME one is written in the writer's session zone — so a guessed column could silently miss rows. `incrementalPullSupport` (and the registry's `resolveIncrementalPullSupport`) reuse `pgIncrementalPullSupport`: `SUPPORTED` when `modifiedAtField` is set, otherwise `NEEDS_CONFIGURATION` (never `NOT_SUPPORTED`); the job then runs a full pull.
- **Mechanism:** `WHERE (<filter>) AND <modifiedAt> > '<since − 60s>'`, the bound a UTC literal `YYYY-MM-DD HH:MM:SS.ffffff` passed as text (no driver Date handling). `newWatermark = new Date()` is captured **before** the first query, so rows changed mid-pull are re-pulled next time; the 60s skew (`applyPgClockSkew`) covers the worker-vs-database clock gap and idempotent commits absorb the overlap. The column is checked up front (`assertMySqlModifiedAtColumnIsUsable`): a missing or non-TIMESTAMP/DATETIME column (DATE included) fails fast with the usable columns listed.
  - **TIMESTAMP** compares as a UTC instant (the session `time_zone` is `+00:00`) — exact.
  - **DATETIME** compares as a naive wall clock, so it **assumes UTC writers** (Rails, Django `USE_TZ`, RDS / Cloud SQL / Azure defaults). A writer west of UTC makes rows get missed until the next full pull; east of UTC only re-pulls extra rows. The setting's description says so.
  - Rows whose modified-at is **NULL are never pulled incrementally** (Postgres parity).
- **Deletions:** not detected on an incremental run; a full pull reconciles.
- **Evidence:** IT only (no CLI incremental pull yet) — `mysql-incremental-pull.spec.ts` drives the real pull job over both column kinds on both flavors (bootstrap, changed-row-only, no-op, skew window, bad `modifiedAtField`); `mysql-connector.spec.ts` checks the `OR` filter stays parenthesized next to the `since` bound.

## Edge cases discovered

Verified against the local MySQL 8.4 / MariaDB 11.4 servers during the build (driver spike and per-slice live checks; details in [`LOG.md`](./LOG.md)):

- A **string** constant compared with an integer column is converted loosely: `id = '12abc'` matches row 12 and `'9.007199254740993e15'` matches row 9007199254740993 (MySQL documents a DOUBLE comparison; on MySQL 8.4 / MariaDB 11.4 all-digit text compares exactly, but the loose conversion of non-integer text reproduces on both). Integer ids (and integer-valued DECIMAL ids) are therefore bound as BigInt (rendered as an unquoted literal); non-integer text for an integer key is "unmatchable" and never sent.
- `insertId` is a number below 2^53 and a string at or above it; ids above 2^53 round-trip exactly.
- With `FOUND_ROWS`, a no-op UPDATE reports 1 affected row; `UPDATE … LIMIT 2` / `DELETE … LIMIT 2` over 3 matching rows report 2 on both flavors — the multi-row guard works, and a non-unique chosen id rolls back with every row unchanged.
- MySQL 8.4 **rounds** a fraction written into a precision-0 DATETIME (`…:05.678` → `…:06`, carrying into the next day/year); MariaDB 11.4 **truncates**. Both report precision 0 as plain `datetime`, so the write path truncates to the column's precision itself.
- MariaDB flags a column as JSON (`extendedFormat: 'json'`) for ANY column-level CHECK whose top-level AND list contains `json_valid(...)` — including VARCHAR / TEXT columns — but not for table-level checks or a JSON column whose own CHECK replaced the implicit one.
- mysql2's own JSON parse (≥3.23) turns integers above 2^53 inside documents into strings; the decoder parses the raw text itself.
- GEOMETRY bytes carry the 4-byte SRID prefix (`e6100000` for 4326) before the WKB.
- A `?` inside double quotes or after `#` IS substituted by the client-side formatter (it would consume a LIMIT / watermark binding); inside backticks / single quotes it isn't. A `?` written directly inside backticks in `knex.raw` is still counted by knex as a placeholder — identifiers always go through `??`.
- A plain object binds as `'[object Object]'` and an array as a comma list (shifting later columns) → every object / array / JSON value is `JSON.stringify`'d first.
- A hostile global `sql_mode='ANSI_QUOTES,NO_BACKSLASH_ESCAPES'` is overridden by our session `sql_mode`; `a'b\c` round-trips byte-exact.
- `_ci` / PAD SPACE collations: an update by `abc` matches stored `ABC`; the per-row fallback read-back returns the stored spelling.
- MySQL 8.4 fills 190 MEDIUMTEXT columns but not 200 (1118 row size), hence `maxFieldsPerTable: 180`; MariaDB 11.4 handles 200. 180 MEDIUMTEXT fields × 2,000 `é` filled on both.
- `ALTER TABLE … ADD COLUMN …, ADD CONSTRAINT … FOREIGN KEY …` is atomic on both flavors.
- A generated-column write fails with 3105 on MySQL and 1906 on MariaDB; MariaDB's statement-timeout error 1969 has no `code`.
- Wrong database as the scoped `test` user → 1044 (privilege check first); as root → 1049.
- mysql2 mutates `ssl.rejectUnauthorized` on the passed object and throws on a frozen one → a fresh ssl object per client.
- caching_sha2_password works over plaintext (RSA key exchange) and TLS; mysql_native_password needs `--mysql-native-password=ON` on 8.4.
- MariaDB reports `COLUMN_DEFAULT = 'NULL'` (a string), `int(11)` display widths and lower-case `on update current_timestamp()`; MySQL functional unique indexes (`UNIQUE((lower(email)))`) have a NULL column name and are excluded.
- MySQL's GIPK `my_row_id` (invisible, `bigint unsigned`) works as a writable table's id.
- MariaDB `SEQUENCE` objects aren't listed; implicitly system-versioned tables are fully writable.
- MariaDB's catalog collation (`utf8mb3_general_ci`) ignores case and accents, so with `lower_case_table_names=0` a plain `GROUP BY TABLE_NAME` merges `Orders` / `orders` (and `café` / `cafe`). Discovery groups and joins catalog names byte-exactly (`CAST(… AS BINARY)`); MySQL 8's catalog is `utf8mb3_bin` there and was never affected. Covered by `mysql-catalog-collation.spec.ts`.
- INT / BIGINT / YEAR / DECIMAL(p,0) round a fractional value half **away from zero** on store (3.7 → 4, -2.5 → -3), with no strict-mode error. FLOAT / DOUBLE(M,D) store `floor(x) + rint((x − floor(x))·10^D)/10^D`: an exact binary tie goes to the even digit (1.125 → 1.12), and at D=0 a tie goes **down** (0.5 → 0, -0.5 → -1).
- TIME always reads back as `[-]HH:MM:SS[.fraction padded to fsp]` (hours ≤ 838, never `D HH:MM:SS`); TIME(0) **rounds** on MySQL 8.4 and **truncates** on MariaDB 11.4, so the write path truncates to the fsp itself.
- `ENUM` / `SET` declared `CHARACTER SET binary` (or in a `DEFAULT CHARSET=binary` table) arrive as bytes; MySQL 8.4 reports their `CHARACTER_SET_NAME` as NULL, MariaDB as `binary`.
- A FLOAT key's pulled 6-digit rendering never equals the stored float32 (`k = '1.1'` matches nothing); a BIT key sent as text (`'5'`) is read as the byte 0x35. A TIMESTAMP key pulled as `…Z` isn't a valid DML literal (MySQL 1292; MariaDB silently matches nothing).

## Gotchas

- **TIMESTAMP is the one representation rewrite.** Our session runs at `time_zone='+00:00'`, so MySQL prints a TIMESTAMP in UTC; the decoder rewrites `2026-01-02 03:04:05.678` to `2026-01-02T03:04:05.678Z`. That is a lossless rendering of the instant the server reported — the same ruling as the Postgres Date → ISO serialization (DEV-10777) — done as text (not through a JS `Date`) so all six microsecond digits survive. Zero dates (`0000-00-00 …`) stay verbatim.
- **DATE and DATETIME are verbatim** (`YYYY-MM-DD`, `YYYY-MM-DD HH:MM:SS[.f]`). DATETIME has no zone, so its schema uses the non-asserting `date-time-local` format.
- **Binary values are base64 and read-only.** BINARY / VARBINARY / BLOB are the base64 of the exact bytes; GEOMETRY is the base64 of MySQL's internal format (4-byte little-endian SRID + WKB). JSON can't carry raw bytes, and writing the text back would store the text's bytes, so an edit fails with `NonWritableFieldEditError` (reason NotYetSupported). A binary **id** (BINARY(16) UUIDs) is bound back as its bytes, so such rows can still be updated / deleted.
- **BIT is a number, read-only.** BIT(n ≤ 53) is its unsigned integer value, wider BITs a decimal string. Not base64: BIT(1) is Hibernate's boolean mapping, and `'AQ=='` would be unreadable.
- **JSON precision above 2^53 is lost**, exactly like the Postgres connector's jsonb (`{"big": 9007199254740993}` pulls as `9007199254740992`); we deliberately avoid mysql2's alternative, which mutates such integers into strings. MySQL normalizes document key order / whitespace, MariaDB stores the text verbatim. **MariaDB JSON** is detected from MariaDB's own result metadata (`SELECT * … LIMIT 0`, `extendedFormat: 'json'`), not reconstructed from `CHECK_CONSTRAINTS`, so the schema and the row decoder can never disagree (a disagreement would make the write path re-stringify a pulled string). A proxy that drops MariaDB's extended metadata makes those columns plain text; a column the account can't `SELECT *` yields an empty set and a warning (safe direction).
- **`''` becomes NULL in typed columns**: numeric (incl. BIGINT / DECIMAL / YEAR), DATE / DATETIME / TIMESTAMP, JSON, TIME and MariaDB UUID / INET4 / INET6 (strict mode would reject `''` there anyway). Consequence: a stored JSON string document `""` round-trips as NULL (Postgres parity). The canonicalizer treats `''` ≡ null ≡ absent for exactly those columns.
- **Updating a row that no longer exists throws — a deliberate difference from Postgres.** Postgres returns the sent file as if the update worked; MySQL throws `RecordNotFound` with `errorCode: RemoteRecordNotFound` ("surface failures; never silently succeed"). The batch rolls back, the publish runner retries per record, so only the vanished record fails, and Live Export offers its "run a full sync" recovery. Deleting an already-deleted row is tolerated.
- **The UTC session changes `DATETIME DEFAULT / ON UPDATE CURRENT_TIMESTAMP` for rows Scratch writes.** Every Scratch session sets `time_zone='+00:00'` (reads and writes depend on it), so those defaults — and `NOW()` in triggers — produce **UTC wall clock** on rows Scratch inserts or updates, while the customer's own app on a `SYSTEM`-zone server writes local time. TIMESTAMP columns are unaffected. The same UTC assumption drives the DATETIME incremental watermark.
- **Filter validator false positives** (`mysql-filter-validator.ts`; the filter is spliced into `WHERE (…)`): `?` is rejected **everywhere, even inside quotes** (`name = 'what?'`, `` `Featured?` = 1``) — use `LIKE` with `_`; `"` and `\` are rejected everywhere (use `'…'` with `''` doubling); comments, `;`, `@` and `:=` are rejected outside quotes; **keywords must be backtick-quoted** when used as column names (`` `comment` ``, `` `update` ``, `` `set` ``, `` `table` ``, `` `values` ``, `` `lock` ``, …); `INSERT(…)` (the string function) and `user()`, `database()`, `schema()`, `version()` etc. are blocked. Quoted `@`, `#`, `--` and keywords are fine (`email = 'a@b.com'`). **Known gap:** a user-defined stored function called by its bare name in the default database (`my_func(x)`) isn't blocked — database-qualified and backtick-quoted calls are; the follow-up is a built-in-function allowlist (shared with Postgres).
- **Canonicalizer lossiness** (`mysql-field-value-canonicalizer.ts`, the DEV-10556 diff framework that makes a Live Export re-run into MySQL a no-op): temporal values reduce to the literal the write path sends — offsets → UTC wall clock and the fraction **truncated** to the column's fsp (`…:27.600` ≡ `…:27` for DATETIME(0)); DECIMAL(p,s) is rounded half away from zero to its scale (`1.23456` ≡ `1.2346` in DECIMAL(10,4)) then compared as normalized decimal text; BIGINT as normalized text; FLOAT at **6** significant digits (after its `(M,D)` rounding), DOUBLE at **15**; FLOAT / DOUBLE(M,D) first round exactly as MySQL stores them (`floor(x) + rint(frac·10^D)/10^D`); integers / YEAR / whole-number DECIMAL round a fraction half away from zero in decimal text (3.7 ≡ 4), with numeric text parsed and `true`/`false` ≡ 1/0; TIME compares as the written literal (`14:30` ≡ `14:30:00`); CHAR trailing spaces trimmed; ENUM case-folded to the declared member; SET case-folded, de-duplicated and put in declared order; JSON compared as parsed values. These mirror what MySQL stores; the one rule lossier than MySQL is DOUBLE's 15-digit compare, and YEAR's two-digit mapping isn't modelled. An edit that only changes what MySQL would drop is treated as "no change". Read-only columns get no canonicalizer.
- **MyISAM (any non-InnoDB engine) is read-only.** The multi-row guards (`LIMIT 2` → roll back) and `STRICT_TRANS_TABLES` (which only rejects bad values on transactional tables) need transactions. The preview disables creates / updates / deletes, and every write re-checks the engine first (the engine can change after listing) → `UnsupportedStorageEngine` before any DML.
- **Tables whose id isn't AUTO_INCREMENT can't create** (`DEFAULT (uuid())` PKs, natural keys): MySQL has no `RETURNING`, and `insertId` only reports AUTO_INCREMENT values, so a new row couldn't be found again. `DEFAULT_GENERATED` never counts. Updates and deletes work. At write time → `CreateRequiresAutoIncrementId`.
- **`VERIFY_IDENTITY` needs a hostname.** For an IP-literal host mysql2 sends no SNI name and Node checks the certificate against `localhost`, so the credential parser rejects IP + VERIFY_IDENTITY. With a user CA, `ca` is that CA **alone** (adding public roots would defeat the pin); without one it is Node's roots ∪ the Amazon RDS bundle.
- **MariaDB tables with an explicit `PERIOD FOR SYSTEM_TIME` are disabled**: MariaDB adds the row-end column to the PK and every unique key, so there is no single-column unique key. Implicit `WITH SYSTEM VERSIONING` tables work.
- **mysql2 refuses `__proto__`-style column names** (`__proto__`, `__defineGetter__`, …): its row builder throws, so such a table can't be pulled at all.
- **Sparse-JSON update fix.** `changedFields` is a deep sparse diff, so a one-key edit inside a JSON document arrives as `{ meta: { a: 2 } }`. MySQL writes the **whole top-level value** of each changed key from the file (`buildMySqlUpdateChangeSetWithWholeTopLevelValues`), so sibling keys survive (verified live). **Postgres still has the clobber** (`postgres-connector.ts:683`) — follow-up in TODOs.
- **No database host guard.** Nothing vets `databaseHost` before mysql2 dials it (Postgres / Supabase parity), so deployed environments connect to whatever the user typed, internal addresses included. The interim Cloud Run tripwire that refused every deployed connection was removed when the connector was unhidden (2026-10-20); `resolveMySqlNetworkRoute` stays as the seam for the guard (TODO (a)).
- **Connection strings are input only.** `mysql://`, `mariadb://`, `jdbc:mysql://` URLs (plus the `mysql2://`, `jdbc:mariadb://` and SQLAlchemy `mysql+<driver>://` spellings) are parsed by the AuthParser (percent-decoding, unencoded `@ / ? #` in passwords, SSL-mode aliases; every other query parameter is rejected by name, and ADO.NET / Go DSN / `postgres://` / X-protocol / `mysql+srv://` / multi-host JDBC strings get a specific message) into the discrete keys, and **only the discrete keys are stored** — the URL never reaches mysql2, whose own URL parser would turn query parameters into driver options. A URL plus discrete connection fields is ambiguous and rejected; a stored `connectionString` (an old blob written before PATCH ran the AuthParser, or a dev-tools import) is refused at connect and purged by the next edit. Parser errors never echo the URL or password.
- **Session hardening**: explicit `sql_mode` without `NO_BACKSLASH_ESCAPES` / `ANSI_QUOTES` (mysql2 escapes with backslashes client-side, so a customer's `NO_BACKSLASH_ESCAPES` would reopen SQL injection); `STRICT_TRANS_TABLES` makes over-length / bad values fail (e.g. 1406) instead of truncating.
- **Errors never echo raw driver text** (`mysql-error-mapping.ts` keys on `errno` / `code`, never reads `error.message`): network errors name only the host the user typed; 1130 → "allow the IP address 35.233.96.253"; TLS failures → "upload your provider's CA or use REQUIRED". For the data-error allowlist (1054, 1062, 1048, 1364, 1406, 1264, 1265, 1292, 1366, 1451, 1452, 3105, 3819, 3140, MariaDB 1906 / 4025) the redacted `sqlMessage` (≤300 chars, IPs removed) is appended so the user sees the column; never for 1044 / 1045 / 1130 / 1142 / 1143, whose text carries `'user'@'ip'`.
- **DDL commits implicitly**: nothing in `createTable` / `createFields` is transactional, and a failed FK reports that field `failed` while the table stays (`partial`). A table created for a Live Export carries the comment `live_export:<ref>`, where `<ref>` is the create request's ref, the export's source data folder id (`dfd_` + 10 letters and digits; any other ref gets no comment, since other callers pick refs that repeat and knex doesn't escape table comments). A save interrupted after the CREATE leaves the table behind, so the retry's CREATE hits 1050: the table is reused when it is an InnoDB base table carrying that comment, has the injected `id` key and the planned columns, and is empty, checked in that order so a view or a customer's table is never queried for rows (`findMySqlLeftoverTableOwnershipMismatch`, then `findMySqlLeftoverTableColumnsMismatch`, then a row check); anything else fails with "already exists" as before. A 1060 on a plain column always fails, so a column the customer added is never taken over. A 1060 on a foreign-key ALTER counts as created only on the create request's own table (inside `createTable`, or a deferred foreign key whose `createFields` plan carries the `createRef` the table's comment names) and only when the column carries Scratch's named constraint to the resolved target. Text / url / email / phone / select become MEDIUMTEXT (not VARCHAR — the 65,535-byte row limit; select options aren't enforced, Postgres parity), `longText` LONGTEXT, boolean `tinyint(1)`, number: integer `int`, plain / percent `double`, decimal `decimal(p+8,p)` (no precision → `decimal(65,30)`), currency `decimal(scale+8,scale)`, json `json`, date `date` / date-time `datetime(3)`; multiSelect and list fields are skipped with a reason, and a field named `id` is reserved for the injected primary key. A MySQL → MySQL Live Export recreates the exact native `COLUMN_TYPE` when it passes the grammar + allowlist gate (`isRecreatableMySqlNativeColumnType`; ENUM / SET / binary / spatial / zerofill never).
- **TINYINT(1) stays a number** (0/1), not a boolean — the column can hold -128..127; the default view uses a number cell.
- **The id column is read-only and can't be edited from Scratch.** Rows are found by the id in the file, so an edited id would update whichever row already has the new value. The chosen id column is annotated `x-scratch-readonly` (creates only work for AUTO_INCREMENT ids, which MySQL assigns), and `updateRecords` refuses a partial change set that includes the id (`IdColumnEdited`, before any connection) — the message says to revert the edit, or change the id in MySQL and pull again. Residual gap: a change set naming every column (the whole-record fallback) can't be told apart; see TODOs for the runner-level fix.
- **Ids bind in the shape the column stores.** Integer / integer-valued DECIMAL / BIT ids bind as BigInt; DATE / DATETIME / TIMESTAMP ids go back through the write path's temporal converter (so a `…Z` TIMESTAMP id is sent as `YYYY-MM-DD HH:MM:SS[.f]`); BINARY / VARBINARY (and binary-charset ENUM / SET) ids as their bytes. **FLOAT (and BLOB / spatial / VECTOR / unknown) columns are never the id** — the next unique column is used, and a table with no other unique key is disabled in the picker.
- **A non-unique ID field fails the pull (`PulledDuplicateId`).** When the chosen ID field (e.g. an `idFieldOverride`) has no single-column unique index, consecutive rows are compared (across pages) and the first repeat fails the pull instead of paging unpredictably and collapsing rows into one record; the value is never quoted. A by-id pull fails the same way when one id matches several rows. Unique-indexed ids aren't checked (a concurrent insert can legitimately shift a row across a page boundary). Known gap: under a case-insensitive collation, `'a','A','a'` sort as ties in any order.
- **Binary-charset ENUM / SET are base64 and read-only**, like VARBINARY (native type `enum(...) character set binary`, never recreated).
- **CHAR / VARCHAR in a non-utf8mb4 charset aren't recreated verbatim** by a MySQL → MySQL Live Export (latin1 `varchar(255)` is 255 bytes but 1,020 in utf8mb4, so a wide legacy table would hit the 65,535-byte row limit); they fall back to MEDIUMTEXT.
- **Connection-string errors never echo password text.** Once `password=` appears in the query (or when a `?` in a userinfo password started the query), later unsupported / duplicated parameters are rejected without their names, with a hint to percent-encode `& = # % ? / @`; a rejected `ssl={json}` key is named only if it's a known TLS option. The CA bundle is scanned linearly (a 512 KB hostile paste is rejected in ~1 ms).
