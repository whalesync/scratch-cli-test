## Fetchability
| Entity | ✅/❌ | Reason (if ❌) | Workaround |
|---|:--:|---|---|
| Phone Numbers, Users, Contacts, Conversations, Webhooks, Contact Custom Fields | ✅ | — | cursor `overrides` (`pageToken`/`nextPageToken`/`maxResults`/`data`) — **required** |
| Messages, Calls | ❌ global / ✅ scoped | **Required scoping params** — `phoneNumberId` + `participants[]`. No global list (`400` otherwise). | **Verified fetchable when pinned** to a specific phone number + participant(s) as query params (`?phoneNumberId=PNiHiQqGSK&participants=%2B18572229300` → Calls `200` with 1 record, Messages `200`). One endpoint per conversation — not a general/top-level entity. |
| Call Recordings / Summaries / Transcripts | ❌ | **Per-call id in the path**; connector has no templating/fan-out. | Pin a single `callId` per endpoint. |

> **A single conversation's message history can be its own table.** Because each endpoint carries a full URL, you can define a dedicated table for *one* person by pinning the parent ids into the query string — and the cursor pagination then pages through the **entire** thread (e.g. all 1,000 messages with that contact), not just page 1. The trade-off is one table per conversation (no global "all messages"); fine when you specifically want one person's history. Example endpoint:
> ```jsonc
> { "name": "Messages with +1 857-222-9300", "method": "GET",
>   "url": "https://api.openphone.com/v1/messages?phoneNumberId=PNiHiQqGSK&participants=%2B18572229300",
>   "overrides": { "paginationType": "cursor",
>                  "request":  { "cursorParam": "pageToken", "limitParam": "maxResults", "maxPageSize": 50 },
>                  "response": { "cursorPath": "nextPageToken", "dataPath": "data" } } }
> ```
> (URL-encode the `+` in the phone number as `%2B`. Same pattern works for `/calls`.)
