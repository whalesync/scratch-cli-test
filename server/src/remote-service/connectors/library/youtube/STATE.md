## Objects / entity types — what the connector exposes

### 1. Structural entities — define the record path in Scratch
**Record path:** `/{channelTitle}/Videos/{video}.json` etc. (the channel title is a path *segment* grouping that channel's entity tables). Channel **metadata** is no longer a per-channel 1-row table — it lives in a single **top-level `Channels` table** (`wsId: channels`, `remoteId: ['channels']`, `basePath: []`) holding one row per channel involved in the connection (owned + additional public), each row's `id` = the channelId. (Refactored 2026-06-16, DEV-10299 — replaces the old `channel_<channelId>` 1-row table because per-channel 1-row folders broke the general logic.)

| Structural entity | Role | Path segment or grouping? |
|---|---|---|
| Channel title | groups each channel's entity tables (Videos/Playlists/…) | path segment (grouping folder) |
| Channels (table) | one row per involved channel; the FK target | top-level table (`/Channels/`), not nested |

### Access model — what you can actually fetch (two independent axes)
A common point of confusion ("can we only fetch our own channel without an approved app?"). It's **two separate things**:

**Axis 1 — Testing mode (app not Google-verified).** Limits *who* and *for how long*, **not** *what*:
- Only Google accounts added as **Test Users** on the consent screen can connect.
- Refresh token **expires after 7 days** → must reconnect weekly.
- A test user still grants the **full `youtube.force-ssl` scope**, so read **and** write on their own channel works (private videos, captions, edits). **Unverified ≠ read-only.**
- Full public availability (any Google user, no 7-day expiry) requires Google's **app verification** for the sensitive scope.

**Axis 2 — `mine=true` vs. a passed channel ID.** Limits *what data* you see:
- `channels.list?mine=true` returns **only the single channel of the identity you pick on Google's consent screen** (your personal channel, or one brand account if you authorize as that brand). This is the "own channel".
- Any **other** channel must be passed by ID via **Additional channel IDs**. For a channel you **don't own**, you get **public data only** — public videos + metadata; **no** private videos, caption download/edit, or analytics. (This is the "extra channel but limited info" behavior.)
- A managed **brand** channel: to read/write it fully you must authorize **as that brand identity** (so it comes back via `mine=true`); listing it by ID alone gives only public data.

**Net:** to fully pull **and edit** a channel → authorize as the identity that owns it (`mine=true`). To just read another channel's public videos → add its ID. "Approved app" (Axis 1) does **not** gate own-channel read/write for a test user — it only gates non-test-users and token lifetime.

### How to fetch your own channel (local)
1. Add the channel-owning Google account as a **Test User** on the consent screen — `console.cloud.google.com/auth/overview?project=wsv1-test` *(GCP action; human gate)*.
2. Flip the connector `metadata.visible` `false`→`true` **locally** (uncommitted) so it appears in the web-app connector picker — OAuth connectors can't be CLI-connected.
3. Start the client (`:3000`) + this worktree's server; add a **YouTube** connection → OAuth → on Google's consent screen pick the identity that owns the channel.
4. `listTables` returns your channel (`mine=true`) → add it as a table → pull → videos land verbatim.
5. Tick **Include video transcript** on the table's advanced settings before pulling for transcripts; put a channel ID in **Additional channel IDs** for a brand/extra channel.
